# Research Config Template

This template documents the structure of a `research.md` configuration file used by the `/qauto-research` skill. Copy this to your project root (or a custom path) as `research.md` and fill in the sections. The file uses YAML frontmatter for machine-parseable fields and a markdown body for freeform strategy context.

---

## Schema Reference

### Frontmatter Fields

| Field | Type | Required | Description |
|---|---|---|---|
| `schema_version` | integer | Yes | Always `1`. Enables graceful schema evolution. |

#### metrics

Three tiers of metrics control the experiment loop's decision logic.

**metrics.optimize** (array) — metrics the agent actively tries to improve:

| Sub-field | Type | Required | Description |
|---|---|---|---|
| `name` | string | Yes | Metric identifier (must match evaluation output key) |
| `direction` | `"lower"` or `"higher"` | Yes | Which direction is better |
| `target` | number | No | Stop the loop when this value is reached |
| `unit` | string | No | Display unit (e.g., `"ms"`, `"%"`, `"bytes"`) |

At least one Optimize metric is required. The keep/discard decision uses strict Pareto-improvement: all Optimize metrics must be non-regressing AND at least one must strictly improve.

**metrics.guard** (array) — hard constraints that must not be violated:

| Sub-field | Type | Required | Description |
|---|---|---|---|
| `name` | string | Yes | Metric identifier |
| `direction` | `"lower"` or `"higher"` | Yes | The "good" direction (same semantics as optimize) |
| `threshold` | number | Yes | Discard experiment if value is worse than this |
| `unit` | string | No | Display unit |

If any Guard metric is violated, the experiment is discarded immediately — no further checks.

**metrics.track** (array) — informational metrics logged but never acted upon:

| Sub-field | Type | Required | Description |
|---|---|---|---|
| `name` | string | Yes | Metric identifier |
| `unit` | string | No | Display unit |

#### evaluation

Defines how metrics are measured after each experiment.

| Field | Type | Required | Description |
|---|---|---|---|
| `pre_commands` | array of strings | No | Commands to run before evaluation (build, flash, deploy, warm-up). Executed sequentially; any failure = crash. |
| `command` | string | Yes | The main evaluation command that produces metric output |
| `timeout_seconds` | integer | Yes | Max seconds for the evaluation command. Exceeded = crash. |
| `output_format` | `"structured"` or `"regex"` | Yes | How to parse metric values from command output |
| `patterns` | map (string → string) | Conditional | Required when `output_format: regex`. Maps metric name to a regex with one capture group. |

When `output_format` is `structured`, the evaluation command must output JSON with metric names as keys and numeric values. When `regex`, each pattern is applied to the full command output and the first capture group is parsed as a number.

#### scope

Defines what the agent is allowed to modify during experiments.

| Field | Type | Required | Description |
|---|---|---|---|
| `files` | array of strings | Yes | File paths the agent may edit. Paths are relative to the workspace root. |

**V1: file-level only.** The agent must not modify files outside this list during the experiment loop. Exclude test files, evaluation scripts, and build configuration (changing these would invalidate measurements). Exclude generated files (they will be regenerated by pre-evaluation commands).

> **V2 note**: Section-level and parameter-level granularity (restricting modifications to specific functions, blocks, or config keys within a file) is planned for V2.

#### stop

Defines when the experiment loop halts. All conditions are checked after every experiment; the loop stops when ANY triggers.

| Field | Type | Required | Default | Description |
|---|---|---|---|---|
| `max_iterations` | integer | Yes | 50 | Maximum number of experiments (excluding baseline) |
| `max_time_minutes` | integer | Yes | 120 | Maximum wall-clock time in minutes |
| `plateau_window` | integer | Yes | 10 | Stop after K consecutive non-crash experiments with no improvement |
| `consecutive_crash_limit` | integer | Yes | 5 | Stop after N consecutive crashes |

Objective thresholds (defined via `target` on Optimize metrics) also trigger a stop when all targets are met.

#### git

| Field | Type | Required | Description |
|---|---|---|---|
| `tag` | string | Yes | Short identifier for this research run (e.g., `"may12"`, `"v2-ota-speed"`). Branch will be `research/<tag>`. |
| `source_branch` | string | Yes | Branch the research run was started from. Used by `/qclose research` to know the squash-merge target. Populated automatically by `/qauto-research setup` from `git rev-parse --abbrev-ref HEAD`. |

The branch prefix `research/` is hardcoded and not configurable. The dedicated worktree defaults to `../<project-name>-research`.

#### hook

| Field | Type | Required | Description |
|---|---|---|---|
| `enabled` | boolean | Yes | Whether to add a stop hook to the user-level hook config for auto-continuation (Kiro agent config or Claude Code `settings.json`). Set `false` for manual re-invocation. |

---

### Body (Markdown)

The markdown body below the frontmatter provides freeform context for the agent. Suggested sections:

- **Strategy notes** — approaches to try or avoid, algorithmic directions, known dead ends
- **Domain context** — background knowledge relevant to the optimization (physics, protocol specs, hardware constraints)
- **Seeded hypotheses** — specific ideas to test first (the agent uses these as inspiration, not obligation)
- **Hardware/environment notes** — what's connected, how to verify connectivity, environment variables
- **Prior results** — links or summaries of previous research runs, known baselines

The body is optional but strongly recommended. The more context you provide, the better the agent's initial hypotheses will be.

## Example 1: BLE Dongle OTA Optimization

A hardware-in-the-loop example targeting BLE firmware OTA performance on an nRF52840 dongle.

````markdown
---
schema_version: 1

metrics:
  optimize:
    - name: "connection_failure_rate"
      direction: "lower"
      target: 0.02
      unit: "%"
    - name: "ota_transfer_speed"
      direction: "higher"
      target: 45.0
      unit: "kB/s"
  guard:
    - name: "peak_ram_usage"
      direction: "lower"
      threshold: 245760
      unit: "bytes"
  track:
    - name: "average_rssi"
      unit: "dBm"
    - name: "flash_size"
      unit: "bytes"

evaluation:
  pre_commands:
    - "west build -b nrf52840dongle_nrf52840 -- -DOVERLAY_CONFIG=release.conf"
    - "nrfjprog --program build/zephyr/zephyr.hex --sectorerase --verify --reset"
    - "sleep 3"
  command: "python scripts/ble_ota_bench.py --port COM7 --iterations 50 --output json"
  timeout_seconds: 300
  output_format: "structured"

scope:
  files:
    - "src/ble/connection_params.h"
    - "src/ble/ota_transfer.c"
    - "src/ble/ota_transfer.h"
    - "src/ble/gatt_config.c"
    - "prj.conf"
    - "release.conf"

stop:
  max_iterations: 40
  max_time_minutes: 180
  plateau_window: 8
  consecutive_crash_limit: 3

git:
  tag: "ota-speed-v2"
  source_branch: "main"

hook:
  enabled: true
---

## Strategy Notes

Focus on connection parameter negotiation and MTU/DLE optimization first — these
have the highest leverage on transfer speed without touching the OTA protocol itself.
Avoid modifying the bootloader or DFU validation logic (out of scope and risk of bricking).

## Domain Context

- nRF52840 dongle with Zephyr RTOS, nRF Connect SDK v2.6.1
- BLE 5.0 with Data Length Extension (DLE) supported
- Current OTA uses the Nordic DFU protocol over GATT
- Central device is a Raspberry Pi 4 running BlueZ 5.66
- Connection interval range: 7.5ms - 4000ms (BLE spec limits)
- Max ATT MTU: 527 bytes (nRF52840 hardware limit)

## Seeded Hypotheses

1. Increase connection interval to 15ms (currently 30ms) — reduces per-packet overhead
2. Enable DLE with max PDU size 251 bytes — currently using default 27 bytes
3. Request MTU 247 (max for DLE 251 minus L2CAP header) — currently negotiating 23
4. Reduce supervision timeout from 4s to 2s — faster reconnection on drops
5. Batch notification queuing — send 6 packets per connection event instead of 1

## Hardware/Environment Notes

- Dongle connected via nRF52840 DK as debugger/programmer on J-Link
- Serial output on COM7 at 115200 baud
- Test distance: 1 meter line-of-sight (controlled environment)
- Raspberry Pi accessible at 192.168.1.50 (BlueZ central)
- Power supply: USB 3.0 port (stable 5V)

## Prior Results

Previous manual tuning achieved 28 kB/s transfer speed with 3.5% failure rate.
Baseline before any optimization: 12 kB/s, 8% failure rate.
RAM usage has been stable around 180KB — headroom exists up to 240KB (conservative guard).
````
