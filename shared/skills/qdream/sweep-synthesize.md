# qdream sweep — Phase 3: Synthesize

Part of the `/qdream` skill: `SKILL.md` in this directory loads this file when Phase 3 starts (its phase index). The Rules and destructive-path invariants in `SKILL.md` apply here.

### Phase 3 — Synthesize

This phase runs in the Synthesize phase agent (`sweep-handoff.md`, its brief and its § Phases row). It reads `handoff/gather.json`, `handoff/harvest.json`, `sweep/countverify.json` and `sweep/coverage.json`; it then runs `sweep-decide-apply.md § DEC-PROPOSALS` and `§ DEC-RETIRE`, and ends by writing `handoff/synthesize.json`, after `dream-sweep.py gate` has written `handoff/gate.md`. Every memory write in this phase is an op in a `handoff/ops/<step>.json` file, queued with `<python> <skill-dir>/scripts/dream-write.py queue --ops <file> --snapshot-sha <sha>`. `queue` validates it against the file as earlier queued ops leave it and writes no memory file: every write runs later, at `sweep-decide-apply.md § APP-WRITE`, where `memedit` resolves each target by the manifest's parse rules, performs the journal-first triple for every rename and removal, preserves `## Declined`, and records each file's hash. Never edit a memory file with an edit tool. Write each step's outputs to `handoff/steps/<STEP-ID>.json` when it completes.

**Cross-validation gate** `[SYN-GATE]` (named step — runs BEFORE § SYN-WRITE and gates § SYN-PROMOTE). **Full mode only** — lightweight has no verifier (its quote is user-facing prose per `SKILL.md § Lightweight Consolidation`, with no structured `evidence_quote` to check).

Dispatch **one adversarial verifier sub-agent per project**, before any autonomous Write in § SYN-WRITE. Render the briefs with `<python> <skill-dir>/scripts/dream-sweep.py brief --kind verifier --harvest harvest.json` (`--harvest` only when `harvest.json` holds items); launch each verifier with the exact prompt line `brief` printed, at most 5 per batch, one message per batch; collect each return with `extract --kind verifier --label <L>` per label, after `wait` or by your harness's own route, as in `sweep-gather.md` (Collect); then run `<python> <skill-dir>/scripts/dream-sweep.py aggregate`, which joins every item with its verdict in `sweep/synth.json` and must report nothing `missing`. **Rule-7-safe** (Rule 7): `brief` puts only the small `evidence_quote` strings, each item's claim, and the project's session-file paths / line-spans in each verifier's data file — the **verifier** opens the cited session span to spot-check; no phase agent and no orchestrator loads a transcript into its own context. Each verifier covers **all** of its project's `memory_proposals` and `improvement_signals` and returns a per-item verdict, mirroring the refuter idiom of `shared/skills/qreview/full-effort.md § Verification phase` (refute stance; verdict confirmed / plausible / refuted).

**Harvest verifier batches.** The `HARNESS_HARVEST:` signals the Gather phase agent built for projects without an `all tasks` agent (`sweep-gather.md`, § GAT-PLANS harvest) go to no per-project verifier. They go to harvest batches of at most 25 items that hold only this harvest, dispatched in the same parallel round with the brief below. Each item's source is its plan file and item from the side file, and the batch receives each member project's plan archive path. The per-project rules apply per member project inside a batch: the fabrication spot-check's coverage floor is counted over each member project's items on its own (every item of a project that carries ≤10, at least 10 of a project that carries more); an item left without a verdict defaults to refuted for its own project; and a batch that fails to dispatch downgrades every member project under the verifier-dispatch failure rule below. **Verifier brief** (one dispatch per project, or per harvest batch). `dream-sweep.py brief` renders it with this marker line as its first line, and the prompt line it prints opens with the marker; `dream-manifest.py baseline --by-role` sorts the verifier's transcript by it (`sweep-decide-apply.md § APP-STATE`, `tokens_by_role`):

> **Dream Verifier Brief**

- **Tool surface — read-only, declared up front** (so the verifier neither probes for limits nor writes): you may use only `Read`/`Grep`/`Glob`, never Bash or PowerShell, even to read a file. You may `Read`/`Grep`/`Glob` the cited session and project files, **the cited governance `§ section` spans** (passed to you for the subsumption and narrowing tests below), **and the project tree** (`Grep`/`Glob`, read-only, to re-run a `stale_entries` item's quoted check). Beyond that you are read-only, run no scripts, and may not dispatch further sub-agents (`shared/AGENTS.md § Dream autonomy exception`, the canonical sentence): modify no file and write nothing to memory. Return verdicts only. (A verifier that can write is a verifier that can rubber-stamp itself into the store.)
- **Budget and termination**: about 60 tool calls. Your task ends when you return the verdict JSON. If the budget runs out first, return it anyway, partial: list the items you did not reach in `unverified_item_ids` and name the gap in `notes`.
- **Receives**: for each of the project's `memory_proposals` / `improvement_signals` — the claim (`why` / `how_to_apply` for proposals, `observation` / `impact_assessment` for signals), its verbatim `evidence_quote`, and the `source` / `sessions_observed_in` pointer; plus the project's session file paths **and its archived plan paths** (`plans/done/`) — so the verifier can open the cited span, session or plan, to spot-check quotes. **Also receives the Task-4 claims that need adjudicating**: each `subsumed_entries` item (heading + the entry's full body [`Why` + `How to apply`] + `governance_ref` + `subsuming_quote`), each `not_a_conflict` item (heading + the entry's full body [`Why` + `How to apply`] + `governance_ref` + `narrowing_reason` + `governance_span`), and each `stale_entries` item (heading + the quoted failing check in `reason`). **Sourcing the entry body**: `brief --kind verifier` reads each named heading's body from its memory file by the manifest's parse rules and puts it in the verifier's data file; no agent assembles it by hand. **Cost mitigation**: for the subsumption and narrowing tests the data file names the item's `governance_ref`, and the verifier reads **only the cited `§ section` span** of the governance file, not the whole file — a verifier needs the span it is testing entailment against, not `AGENTS.md` in full.
- **Stance — refute**: "Your goal is to refute the claim that each item is entailed by its `evidence_quote`. Look for claims the quote does not actually support, and for quotes that do not appear verbatim in the cited session."
- **Entailment gate (anti-rubber-stamp)**: an item's verdict is **confirmed** or **plausible** ONLY when the verifier cites, verbatim, the span of the `evidence_quote` that entails the claim. A verdict that cannot quote the entailing span verbatim **defaults to refuted** — this guards against a shallow verifier that lazily rubber-stamps entailment (the recorded "dream sub-agents produce shallow analysis" risk). Adapts `shared/skills/qreview/full-effort.md § Verification phase`'s refutation-evidence gate, inverting its default direction: qreview lets a no-quote verdict stand (plausible), whereas qdream fails it closed to refuted.
- **Fabrication spot-check**: check the items' `evidence_quote`s against their cited sources with a **coverage floor** — every item when the project carries ≤10 items; at least 10 items above that, prioritizing those that would drive an autonomous write or a promotion (an unfloored "sample" is not a discharge). A quote whose `source` is an archived plan is checked against that project file (`plans/done/`, plan-slug + section) the same way a session-sourced quote is checked against its session. A quote absent from a **reachable** source is **refuted** (fabricated evidence) regardless of entailment — the verifier reads the span, no phase agent or orchestrator does (Rule 7). **Unreachable-source carve-out** (Rule 4): if the cited session file cannot be opened (rotated/absent), the spot-check is **indeterminate**, not fabrication — judge the item on quote-entailment alone, or surface it as a user-gated proposal; never refute a valid item merely because its source rotated. (regression fixtures: transition-fixtures.md FIX-FABRICATION-*)
- **Subsumption test** (`subsumed_entries` — **no coverage cap; verify every candidate**): for each item confirm the `subsuming_quote` (a) **appears verbatim** in the cited `§ section` span; (b) is a **normative** span — a rule that *asserts* the claim, **not** an Exclusion-List row, a prohibited-command table entry, a non-goal, or a quoted counter-example (governance is full of verbatim spans stating what it *forbids*, and a naive entailment test would read those as licensing a removal); and (c) **entails the entry with no residue — including the entry's `How to apply` operational specifics, not only its claim.** An entry saying *"do X"* against a rule saying *"do X **except when Y**"* is **not** subsumed — its exception is the point; a `How to apply` carrying a flag, a path, or a workaround the rule's principle does not contain is residue. Any residue, non-normative span, or missing quote → **refuted**. (regression fixtures: transition-fixtures.md FIX-SUBSUMED-*)
- **Narrowing test** (`not_a_conflict`): confirm the `governance_span` appears **verbatim** in the cited `§ section`, and that the entry genuinely *narrows or extends* that rule **for the stated `narrowing_reason`** rather than contradicting it. A claimed narrowing **whose `narrowing_reason` does not hold**, or that actually **contradicts** the span → **refuted** (it is a `governance_conflicts` case in disguise, and reclassifying it silently drops a real contradiction from the user's queue). (This is the consumer of `narrowing_reason` — the field is passed in `Receives` above so the test can check the narrowing holds for the reason claimed, per `shared/AGENTS.md § Structure Requires a Consumer`.)
- **Stale-entry re-check** (`stale_entries`): after this plan every Task-4 claim class is verifier-checked *except* the one that drives an autonomous delete — which would be backwards. For each item, **re-run the quoted failing check yourself** (`Grep`/`Glob` the project tree) and return a per-item **staleness verdict**: `confirmed` when the check genuinely fails (the entry is stale), otherwise `plausible`/`refuted`. A `stale_entries` item whose quoted check the verifier finds **passing** is **refuted** — the entry is not stale. (regression fixtures: transition-fixtures.md FIX-STALE-recheck-passing) (Autonomous deletion in § SYN-STALE then requires **four** conditions — a count-verified `task4_status: checked`, a `confirmed` staleness verdict, no `human:` actor on the entry's `Verified`, and a real failing check quoted in `reason`; anything less surfaces in Phase 4b.)
- **Returns** per item: exactly one of **confirmed** / **plausible** / **refuted**, plus the one-line entailing-span citation (for confirmed/plausible) or the refutation reason (for refuted). This applies to `memory_proposals` / `improvement_signals` **and** to each `subsumed_entries`, `not_a_conflict`, and `stale_entries` item — every claim class returns a per-item verdict. Any item for which the verifier returns **no** verdict **defaults to refuted** (fail-closed) — but a default-refute is an **examination gap, not a judgment**: it blocks writing/promotion this run and is NOT recorded to `rejected_lessons` (see Disposition).

**Disposition** (consumed by § SYN-WRITE, § SYN-PROMOTE, **and the § SYN-RECONCILE reconciliation pass** — this third consumer reads the `subsumed_entries` / `not_a_conflict` / `stale_entries` verdicts below):
- **confirmed** items are eligible to be written (§ SYN-WRITE) and to be promoted (§ SYN-PROMOTE). **plausible** items are not written: each becomes a singleton ledger row (`memory-rules.md § Singleton ledger`) and counts toward promotion once a second session supports it.
- **refuted** items are **NOT written autonomously and NOT promoted**; report them in Phase 4b. Additionally, for each **explicitly refuted `memory_proposals` / `improvement_signals` item** — one the verifier actually examined and returned `refuted` for, with a refutation reason — **record it to the `rejected_lessons` suppression store** (written to `synthesize.json`'s `rejected_lessons`, which § APP-STATE's `state apply` persists: the state file is written only there): append `{ "target": "<the file § section or entry heading the item addressed>", "signal": "<one-line description>", "reason": "refuted", "date": "<YYYY-MM-DD>" }` to `.dream-state.json` `rejected_lessons` (`shared/skills/qdream/memory-rules.md § State File Format`) — so the next sweep's Rejected-lessons consult (§ SYN-WRITE below) suppresses the same shallow reflection. **This recording is scoped to `memory_proposals` / `improvement_signals` only** — the store exists to suppress re-proposed *memory reflections* and *governance signals*, so a refuted **`not_a_conflict`** or **`stale`** Task-4 verdict is **never** written to `rejected_lessons` (that entry merely stands or is re-routed — recording it would spuriously suppress unrelated future proposals about its target for the retention window; the `subsumed_entries` disposition below already states the same carve-out, so none of the four Task-4 classes writes here). **Default-refuted items (no verdict returned — verifier truncation, partial coverage) are NOT recorded**: fail-closed governs the write, not the suppression store, and a transient verifier gap must not suppress a possibly-valid lesson for 180 days — the item simply re-enters a later sweep as a fresh proposal. Full mode only.
- **Promotion reuses these per-project verdicts** — § SYN-PROMOTE does NOT dispatch a second verifier; a signal's promotion eligibility is the verdict its per-project verifier already returned (~1 dispatch/project).
- **Subsumption disposition.** A `confirmed` verdict (the quote is normative and the entry has no residue) removes the entry autonomously: a `delete` op with class `subsumption removal`, which `memedit` allows only on that verdict and refuses on a `human:` entry, named in the Report. Every other candidate is **surfaced to the user in § DEC-GATE** (`Remove / Keep / Defer`) showing the entry, the cited governance span, and the verifier's verdict. A **`refuted`** or no-verdict subsumption is surfaced with that verdict shown and is **never** written to `rejected_lessons` ("governance does not subsume X", recorded against X, would suppress unrelated future *proposals* about X for 180 days). **Verifier-failure degrade**: if the verifier could not test a candidate, **surface it anyway with the verdict shown as unavailable — never remove it.** (This is why the reconciliation pass is a third consumer above: the removal is executed in Phase 5, not here.)
- **`not_a_conflict` disposition**: a `confirmed`/`plausible` narrowing is reported as a narrowing (`sweep-decide-apply.md § Report` — it removes nothing, so no user gate); a **refuted** narrowing is **re-routed to the `governance_conflicts` channel** (it was a contradiction in disguise) and surfaced in § DEC-GATE.
- **Stale disposition feeds the § SYN-STALE gate.** A `stale_entries` item's staleness verdict is consumed by § SYN-STALE: autonomous deletion (or salvage-rewrite) requires a **`confirmed`** verdict, a count-verified `task4_status: checked`, **no `human:` actor** on the entry's `Verified`, and **a real failing check quoted in `reason`** (all four — § SYN-STALE conditions (a)-(d)); `plausible`/`refuted`/no-verdict, an unverified `task4_status`, or a human-attested entry → surface in Phase 4b (`Delete / Keep / Defer`). **`subsumed` beats `stale`** — an entry returned in both channels is dispositioned as subsumed (`§ SYN-RECONCILE`), never deleted through the stale path.

**Verifier-dispatch failure — degrade, never silently write**: a verifier that fails to dispatch (dispatch error, timeout) follows `sweep-handoff.md § Failure gate`; on **Skip**, that project's proposals are **downgraded to user-gated `Save / Skip` proposals** surfaced in Phase 4b (the standard non-autonomous proposal idiom) and the Dream autonomy exception is suspended for that project this run. **No path writes unverified content autonomously.**

**Budget exhaustion — resume, do not abandon.** A verifier that dies on a session or token limit is a *different* case from a dispatch failure, and the Skip-downgrade above is the wrong response to it: the verifier input files are still on disk and still re-runnable, so nothing needs re-deriving. Write a `needs-decision` of kind `rate-limit` (with the reset time) or `budget`, naming the unverified item count and the affected projects, and end (`sweep-handoff.md § Failure gate`); the orchestrator offers **`Resume when quota returns`**, and a paused sweep keeps its work folder. On resume, re-dispatch **only** the unverified labels (`--attempt N`) and continue the sweep from § SYN-GATE. Do not downgrade the whole run to user-gated proposals, and do not report the sweep as complete. The crash-recovery journal (§ ORI-RECOVER) does not cover this — it guards a destructive-mutation crash, not an exhausted verification phase.

**Outcome tagging** `[SYN-OUTCOME]` (named step — runs after the Cross-validation gate and before § SYN-WRITE, so § SYN-WRITE's derived-utility Size check and Phase 4b's retirement pass read a current `Outcome`). **Full sweep only** (lightweight tracks no outcomes). This is the closed-loop measurement: grade the governance/memory edits applied in *prior* runs against whether their friction actually stopped.

Read `.dream-state.json` `outcome_tags` (`shared/skills/qdream/memory-rules.md § State File Format`): each record carries the `target` (a file § section, or an entry heading) and the `applied` date of a past edit. For each record still unresolved (no `outcome`/`checked` yet), compute a **binary recurred / not-recurred**, keyed by that `applied` date + `target`:
- **Rule-7-safe compute — reuse the sub-agents' signals, never load a transcript**: the edit's friction has **recurred** iff this sweep's **Cross-validation-gate-confirmed** `improvement_signals` (from Phase 2, `confirmed`/`plausible` verdicts only) still report a semantically equivalent friction against the same `target`, observed in a session or plan dated **after** `applied` — a signal the gate **refuted** is **not** evidence of recurrence (do not let an unverified signal stamp `recurred`, an autonomous write that lowers utility and tees the rule up for retirement — that would bypass the Cross-validation gate on this path); `insights_signals` are **not** gate-verified, so a recurrence seen *only* in `insights_signals` is advisory and cannot alone stamp `recurred` — checked against `sessions_observed_in` / evidence dates (metadata, not transcript text; no phase agent or orchestrator opens a session file, Rule 7). **Match on the signal's `observation` content, not merely its `target_file`**: signals carry a file-level `target_file` (no section), so for a section-granular `target` (`file § section`) a recurrence counts only when the signal's observation is semantically equivalent to *that specific edited rule/section* — a *different* friction in the same file must NOT be scored as recurrence (else an unrelated same-file signal would falsely tee the rule up for retirement). If such a post-edit recurrence exists → `recurred`. If the `target`'s project *was* read by an agent this sweep and no such friction surfaced → `not-recurred`. If the `target`'s project was **not** read by an agent this sweep → leave the record unresolved (re-check next sweep); do not guess. **Read by an agent** means a project with an `all tasks` dispatch this sweep; the Report's `Projects analyzed` count uses the same set. It governs here and in the retention rule below: a `Tasks 4-5 only` dispatch reads no sessions, and the harness harvest alone reads no project.
- Set the record's `outcome` to `recurred`/`not-recurred` and `checked` to today, in `synthesize.json`'s `outcome_tags` (persisted by § APP-STATE's `state apply`).
- **Feed the two consumers**: for a **memory-entry** `target`, stamp the entry's `Outcome:` metadata field (`recurred <date>` / `not-recurred <date>`, on its own line beneath the Source/Verified line, never after the Verified value; `shared/skills/qdream/memory-rules.md § Cross-type optional metadata`) so § SYN-WRITE's derived-utility Size check reads it: a `memedit` `replace` op carrying the whole entry with the field set (an autonomous memory write, within the Dream autonomy exception). For a **governance-edit** `target`, the `outcome_tags` record is the input to Phase 4b's **governance retirement pass** — a `recurred` outcome is evidence the applied rule did not prevent its friction, i.e. a retirement candidate.
- **Retention (bounded growth — `outcome_tags` must not accumulate forever)**: once a record is resolved and consumed, prune it — drop a `not-recurred` record after its memory `Outcome` is stamped / its retirement input is read; keep a `recurred` record only until its targeted rule is retired or re-affirmed, then drop it. Resolve-and-drop an *open* record that has survived **3 sweeps that read its `target`'s project by an agent** without a recurrence (treat as `not-recurred`). This bounds the array so the closed loop does not itself become an accretion sink.

1. **Aggregate memory proposals** `[SYN-WRITE]`. For each proposal from sub-agents:
   - **Authority hierarchy check**: Verify the proposal does not contradict **governance** (AGENTS.md / SKILL.md — the top of the order in `shared/AGENTS.md § Authority hierarchy`). If it contradicts governance, do **NOT** write it — a memory entry may not silently override governance. Escalate to the user in Phase 4b with an explicit **action set** — `record with an explicit override note` / `propose a governance update` / `drop` — never a bare do-not-write ban (a ban with no destination silently drops information the user may still need). A user `drop` **appends a canonical heading-keyed `## Declined` row** — `- "<dropped proposal heading>" — declined <YYYY-MM-DD> (dropped: contradicts <file § section>)`, a `memedit` `declined_add` op the Apply phase agent queues under that gate item's decision — so the dedup gate's declination consult suppresses re-proposal; `record with an explicit override note` is Phase 5's `insert` of the shown entry, and `propose a governance update` writes no memory op (`sweep-decide-apply.md § APP-ADJUDICATE`, memory-proposal decisions). A contradiction with a higher *memory* tier (user memory > higher-order > project memory — **not** governance) is a different case, handled by the Dedup check below and `shared/skills/qdream/memory-rules.md § Dedup Check Procedure`, which **may** record it with an explicit override note.
   - **Rejected-lessons consult** (full mode only): before deduping or writing, check the proposal against `.dream-state.json` `rejected_lessons` (`shared/skills/qdream/memory-rules.md § State File Format`) — consulting only records **dated before this sweep** (each record carries a `date`; a suppression appended earlier in *this* run must not drop a same-sweep, cross-project **confirmed** proposal — dating is day-granular, so a record dated the same day as this sweep is treated as same-sweep and not consulted, and a quote's date is the date of the session or plan it was drawn from; tie rules: `shared/skills/qdream/memory-rules.md § Date References`). If it matches a suppressed signal — same `target` and a semantically equivalent one-line description previously recorded `refuted` or `skipped` — **suppress it** (do not dedup, write, or re-propose the same shallow reflection a prior sweep already suppressed) — **unless it re-surfaces with fresh grounded evidence**: a verbatim `evidence_quote` dated *after* the suppression record's `date`, across **2+ distinct** post-suppression observations. A later in-session user `Save` of the signal (a row whose in-session token is dated on or after a `skipped` record's `date`) also overrides that record: the sweep treats it as cleared and drops it. On such re-surfacing do **not** suppress — drop the now-stale `rejected_lessons` record and let the proposal proceed to the Cross-validation gate for re-adjudication, so a lesson that genuinely became true is re-learnable rather than permanently locked out (`shared/skills/qdream/memory-rules.md § State File Format`, `rejected_lessons` retention). This consult lives here in the full-mode Phase-3 gate, deliberately **not** in the shared `shared/skills/qdream/memory-rules.md` write-time gates, so lightweight mode (no `.dream-state.json`, no verifier) stays clean. The **same consult governs the improvement-signal paths** (§ SYN-PROMOTE promotion and below-threshold persistence), so a prior-sweep-suppressed signal is not re-promoted or re-accumulated there either.
   - **Dedup check**: Scan the target memory file — the one `shared/skills/qdream/memory-rules.md § Resolution contract` returns (for a user-scope signal, `memory/topics/improvement-signals.md`); this is a read, not a creation — for entries with similar heading or overlapping content. If related entry exists, merge/update instead of creating new. When the merge keeps the entry under a **different heading** (the `Merge Strategy` heading-preference), that is a **rename**, not a removal: record it in the working map below so the reconciliation pass **re-points** every node pointer naming the old heading. **Attestation lapse**: when a merge's surviving `Verified` no longer carries the `human:` actor the replaced entry's `Verified` carried (the surviving `Verified` carries any actor other than that `human:` id), record the surviving heading for the Report's `Attestations lapsed on merge` line (`sweep-decide-apply.md § Report`). This holds, for example, for a verifying merge and for a non-verifying merge whose newer surviving date carries `sweep`. The merge rule itself is unchanged (`shared/skills/qdream/memory-rules.md § Merge Strategy`). (regression fixtures: transition-fixtures.md FIX-MERGE-human-lapse-verifying, FIX-MERGE-human-lapse-nonverifying)
   - **`Usage` bump**: for any existing entry this sweep relied on — the dedup check merged into it, or it was found referenced in an analyzed session or a recent plan (a plan's `Memory relied on` header counts only through the plan feeder below, so a heading the feeder leaves unresolved bumps nothing) — increment its `Usage` counter (at most once per entry per sweep, a `memedit` `usage_bump` op) per `shared/skills/qdream/memory-rules.md § Derived Utility & Pruning`. This must run before the Size check so the derived-utility order reads a current counter.
     - **Plan feeder (deterministic; `<python> <skill-dir>/scripts/dream-sweep.py feeder`)**: the script computes the feeder below into `sweep/feeder.json` — its `usage_bump` ops, the unresolved and dropped headings and the `Usage from plans` line — and `dream-write.py queue --ops sweep/feeder.json` queues the bumps; never match headings by hand. A heading at an index in `memory_relied_on_truncated.shortened` was cut at 200 characters: do not match it, report it as truncated. Headings past the 20-heading cap (`total` − `kept`) are absent from the list: report their count as dropped by the manifest cap. Match each heading against the entry headings (`###` lines, without the `### `) in exactly three places: that project's memory file (`shared/skills/qdream/memory-rules.md § Resolution contract`), the config repo's `memory/MEMORY.md`, and every `memory/topics/*.md` (read each file once; inside the config repo the project file is its workspace store's `memory/MEMORY.md`, `shared/skills/qdream/memory-rules.md § Resolution contract` step 0, not user memory). Never guess between candidates.
   - **Size check**: propose no prune here.    - **Record renames and removals into the sweep's working map** (the input to the Support-set reconciliation pass): that pass runs **after** this step, so it cannot re-derive what you renamed or removed — `memedit` records each rename (a `replace` op whose text changes the heading) and each removal (a `delete` op with its removal class) into the working map *before* it mutates (per the journal-first rule), then flushes, then mutates. 2. **Process stale entries** `[SYN-STALE]`: Handle entries returned in `stale_entries` — verification-failed, or reachable-and-contradicting provenance. One item is never deleted or salvage-rewritten autonomously, whatever its verdict, and is always surfaced in § DEC-GATE (`Delete / Keep / Defer`): a stale item whose heading is also in this sweep's `governance_conflicts` for the same memory file (shown beside the conflict, which the user adjudicates first). (regression fixtures: transition-fixtures.md FIX-STALE-user-memory, FIX-STALE-fresh-conflict) (Governance contradictions are **not** stale entries; they arrive in `governance_conflicts` and are never deleted autonomously — see § SYN-RECONCILE.)
   - **Disposition gate — never delete or salvage-rewrite a stale entry without verification.** The phase agent applies it; it is not sub-agent routing. Task 4 emits `stale_entries` cheaply (a grep) but `subsumed_entries` expensively (read governance), so under context pressure a subsumable entry can land in `stale_entries`, and it must not be deleted with no user gate. A `stale_entries` deletion **or a § SYN-STALE salvage-rewrite** runs autonomously only when all **four** conditions (a)-(d) hold, the same four as `SKILL.md`'s "Stale deletion needs all four conditions": (a) `task4_status` is `checked` **and count-verified** — the union of Task-4 class headings equals the file's entry headings, a check `<python> <skill-dir>/scripts/dream-sweep.py countverify` already computed at Gather into `sweep/countverify.json`; read it here, **before any autonomous stale deletion**. The "(§ SYN-RECONCILE)" reference is *definitional* — it names where the union check is specified — **not** an ordering dependency on the not-yet-executed § SYN-RECONCILE: the set-comparison is stateless, computed from the returns against the file's entry headings in the manifest (the side file's `entries[]` for a project file, `user_memory.json` for a user-memory file, § SYN-RECONCILE), so it must not be deferred to the downstream step (deleting on the self-reported `checked` would reopen the self-report hole). **And** (b) the item carries a **`confirmed`** staleness verdict from the Cross-validation gate (which re-ran the item's quoted failing check, § SYN-GATE). If (a) or (b) fails — Task 4 skipped or its coverage incomplete, or the verdict is `plausible`/`refuted`/absent — **surface** the stale entries in § DEC-GATE (`Delete / Keep / Defer`, showing the type-verification evidence), executed through the **same `sweep-decide-apply.md § Phase 5 — Apply` path** as a `Delete entry` adjudication (removal class `stale-entry deletion`; a surfaced item with no executor would never be decided). The gate governs **salvage-rewrites** as well as deletions — a rewrite mutates a possibly-conflicted entry as irreversibly as a delete for evidence purposes. **`subsumed` beats `stale`**: an entry returned in **both** channels is dispositioned as **subsumed** (§ SYN-RECONCILE: removed on a `confirmed` verdict, except a `human:` entry, otherwise the Phase 4b `Remove / Keep / Defer`), never deleted through the stale path here.

     **Conditions (c) and (d), with different destinations when they fail:**

     - **(c) Human-attested entries.** If the item's `entry_verified` carries a **`human:`** actor (`shared/skills/qdream/memory-rules.md § Memory File Format`), never delete or salvage-rewrite it autonomously, however well-formed the staleness verdict. A person confirmed this entry; an agent re-running a grep is not independent evidence against that (`memory/HIGHER_ORDER.md § Pattern` — *"self-inspection is not verification"*). Surface it showing both the failing check and the human attestation. Same shape as the human-attestation carve-out on demotion (`memory-rules.md § Type Taxonomy`), applied to the delete path.
     - **(d) Expiry-only items.** If the item's **only** staleness signal is `expiry_fired: true` — no failing type-specific check quoted in `reason` — it is **not stale at all** and must not be in `stale_entries`. Treat it as a Task-4 defect: do not delete, do not surface as stale; the entry simply got re-verified this run (a `human:` entry is neither gated nor re-dated: `sweep-gather.md`, Human-attested expiries). A fired `Stale-after`/`Stale-when` is a re-verification trigger, never evidence (`memory-rules.md § Cross-type optional metadata`). **This is the inversion to guard against**: an expiry date reads like a verdict and is not one. The one exception is a `user memory` `pattern` entry: with no project tree to check, its expiry is its type-specific check (`sweep-gather.md`, Task 4), so its item quotes that expiry in `reason` and is surfaced in § DEC-GATE, never deleted.
   - **Salvage before deleting**: an entry carries two payloads — a `Why` (its rationale) and a `How to apply` (its procedure). When the *procedure* is stale but the *rationale* still holds, **rewrite the entry to agree** rather than deleting it. Delete outright only when the rationale is dead too. The rationale is the scarcest thing in a memory file — it is the part someone actually paid for — and a delete-only path throws it away with the part that was merely outdated.
   - **A fifth blocker, outside (a)-(d): never autonomously delete or rewrite an entry carrying any non-terminal `Governance-conflict` record** (`rule-update-pending`/`deferred`, `shared/skills/qdream/memory-rules.md § Governance-conflict adjudication`): such an entry holds an unresolved user adjudication. Even if it fails its type-specific verification (a `rule-update-pending` entry legitimately can, while its requested rule change is still pending), do **not** delete it or salvage-rewrite it here — surface it in § DEC-GATE showing **both** the staleness evidence **and** the pending adjudication, so the user resolves both at once. An autonomous removal or rewrite here would permanently suppress the conflict. (regression fixtures: transition-fixtures.md FIX-STALE-*, FIX-DEMOTE-*)
   - Execute each disposition as a `memedit` op — a deletion as a `delete` op with its removal class (`demoted` for a provenance auto-demotion, `stale-entry deletion` for a type-verification failure), a salvage-rewrite as a `replace` op carrying the whole rewritten entry — and record why in `steps/SYN-STALE.json` for the Report. `memedit` records each one into the sweep's rename/removal working map *before* it mutates (per the journal-first rule in § SYN-WRITE), in the form the reconciliation pass reads: every **deleted** entry as `target → removal class`, and every **salvage-rewrite that changed the heading** as an explicit `old target → new target` pair, both under the **fully-qualified** pointer target — `user memory § <heading>` / `project memory (<project-path-key>) § <heading>` (§ SYN-WRITE's keying rule), never a bare heading. A prose note of "what was deleted" is not enough — the reconciliation pass reads the map, not the narrative.

3. **Reconcile memory against governance — the five-way disposition** `[SYN-RECONCILE]` (a `confirmed` subsumption is removed autonomously; every other class is surfaced): this pass reads Task 4's five-way classification (`unrelated` / `not_a_conflict` / `subsumed_entries` / `governance_conflicts`, plus `stale_entries`) and routes each class; it also re-raises recorded adjudications (below). **First, count-verify `task4_status`**: accept `checked` only when the union of headings across the four Task-4 class lists equals the memory file's entry headings — a mechanical set-comparison with no file read (no Rule-7 cost), computed by `<python> <skill-dir>/scripts/dream-sweep.py countverify` at Gather (`sweep/countverify.json`, one status per memory file; split-project chunk returns merged); read its result, never recompute it. The basis is the manifest: a project memory file's entries in its side file's `entries[]`, and a user-memory file's (the config repo's `memory/MEMORY.md` or a `memory/topics/*.md` file) in `user_memory.json` (`file`, `heading`, `ordinal`; a heading that occurs twice counts twice), so no memory file is read for the count. An **incomplete** union is treated as **`skipped-context-budget`** regardless of the self-report: a context-starved sub-agent *truncates* — dropping entries the coverage check catches mechanically — so it cannot fake coverage by omission. Count-verify only the memory files whose Tasks 4-5 ran this sweep (an `all tasks` or `Tasks 4-5 only` dispatch, user-memory files included). A quiet project's file has no Task-4 return this sweep: it is not checked, and that is not an omission. Deleting the entry destroys the only evidence that governance drifted; editing the rule bypasses the user's approval gate. The `shared/AGENTS.md § Authority hierarchy` ("governance wins") is a **read-time precedence** rule for *acting* under conflict — it is not a licence to *delete the dissenting record*, and it is not a claim that the rule is the more current artifact.

   **Reconcile fresh detections against recorded adjudications — before surfacing.** Reconcile the freshly-detected `governance_conflicts` and `subsumed_entries` against recorded adjudications **before** surfacing them to Phase 4b. **Episodic replay ledger + higher-order synthesis** `[SYN-HIGHERORDER]` (named step — runs after § SYN-INSIGHTS). **Full sweep only** — lightweight neither replays episodes nor writes the higher-order tier. 1. **Append to the episodic replay ledger**: for this sweep's confirmed findings — the confirmed `memory_proposals` / `improvement_signals` written in § SYN-WRITE and the stale/demoted entries processed in § SYN-STALE — append a compact record to `.dream-state.json` `episodic_ledger` (`shared/skills/qdream/memory-rules.md § State File Format`): `{ "what": "<one-line what happened>", "where": "<session-id or plan-slug>", "when": "<YYYY-MM-DD>", "outcome": "<written|updated|demoted|refuted|...>", "support_set": ["<pointer to the entry or evidence>", "..."] }`. **Append-only** — never rewrite prior records. 2. **Synthesize higher-order nodes** (autonomous write, Dream autonomy exception). **Entailment constraint — induce, never invent**: a higher-order node must be **induced from its `Support-set`**, not derived from general knowledge or from your own reasoning *about* the project. A derived, model-authored layer sitting over ground truth is exactly the structure that goes wrong when it is allowed to paraphrase freely; the `Support-set` and the tier's sub-ground-truth authority rank (`shared/AGENTS.md § Authority hierarchy`) are what keep it honest. Now, reading the freshly-appended episodes plus a **bounded window of prior ledger records — the most recent 50 by `when` date, never the full history** (the ledger is append-only and unbounded, and an unwindowed read would grow phase-agent context without bound, against Rule 7's intent; deeper re-induction over the accumulated history is the roadmapped episodic-replay-windowing item, `plans/ROADMAP.md`) — together with the **existing** `memory/HIGHER_ORDER.md` nodes noted at Orient (§ ORI-READMEM), induce or update higher-order abstractions — a lesson that generalizes several episodes/entries, a cross-project pattern, a recurring decision rationale. Write each to `memory/HIGHER_ORDER.md` (config repo) as a `memedit` op (`insert` for a new node, `replace` for an update, never before the ledger write above) under its type section in the tier format (`shared/skills/qdream/memory-rules.md § Higher-Order Tier`), with a **`Support-set`** field naming the concrete things it abstracts — an `episodic_ledger` record, a **user or project** `memory/MEMORY.md` entry, an **archived plan**, or a **session**, and **never** a governance section. Write every pointer in the grammar at `shared/skills/qdream/memory-rules.md § Higher-Order Tier`, or the next sweep cannot resolve it. Because Phase 1 re-read the prior nodes into this sweep's input, the abstractions **compound across sweeps** rather than being re-derived from scratch — this re-entry is the consolidation-sweep consumer that keeps the tier from being dead structure (`shared/AGENTS.md § Structure Requires a Consumer`). A higher-order node ranks below user memory and below governance and is read-time advisory (`shared/AGENTS.md § Authority hierarchy` — an abstraction never outranks its own ground truth) — never write one that contradicts governance; apply the same authority-hierarchy check as § SYN-WRITE's proposals.

   **Budget-aware node writes.** `memory/HIGHER_ORDER.md` counts toward the user-memory word pin (`MEMORY_BUDGET_WORDS`; read it from `dream-check.py budget`'s `memory` row, never copy the number), yet no node is ever a routing or prune candidate. Removing a node stays user-gated (`Keep node / Remove node / Defer`, `sweep-decide-apply.md § DEC-GATE`); this rule never deletes one.

   **Required node fields — inlined here so the writer is held to the format without following a citation** (this writer drifted once *despite* citing its spec, so the spec is restated at the point of writing). Every node you write or update MUST carry all five: `**Why**`, `**How to apply**`, `**Source**`, `**Verified**`, and `**Support-set**` (full format block: `shared/skills/qdream/memory-rules.md § Higher-Order Tier`). `**Affirmed**` is **optional**, written **only by § APP-ADJUDICATE**'s `Keep node` branch — **never mint one here**; an existing one is preserved or dropped per the two rules below.

   **Pointer grammar — inlined** (a tight restatement; full grammar and resolution rules: `shared/skills/qdream/memory-rules.md § Support-set referential integrity`). Every `Support-set` pointer names exactly one legal target, in one of these forms — and **never** a governance section:
   - `episodic_ledger #<N>` — a ledger record, `<N>` its 1-based index;
   - `user memory § <heading>` or `project memory (<project-path-key>) § <heading>` — a base `memory/MEMORY.md` entry, `<heading>` the entry's heading text (the `###` line, marker and trailing space stripped) matched character-for-character, a project pointer path-key-qualified;
   - `<plan-slug> § <section>` — an archived `plans/done/` plan;
   - `session <session-id>` — the least durable form; prefer any of the above.

   **Pre-queue self-check.** Before queueing a new or updated node, **re-read its op's text** and confirm: (a) all five required fields are present; (b) every `Support-set` pointer matches one of the grammar forms above; (c) any pre-existing `Affirmed` line was preserved (content update) or correctly dropped (you changed the `Support-set` — the two rules below). If any check fails, fix the op before queueing it.

   **`Affirmed` — preserve it on a content update; drop it when you change the `Support-set`.** A node's optional `**Affirmed**: <YYYY-MM-DD>` line is the **only** persisted state a node carries (`shared/skills/qdream/memory-rules.md § Higher-Order Tier`) — a `Support-set` pointer carries **no** marker, no removal class, and no date. Two rules, and they are exhaustive:

   - **You update a node's *content*** (`Why` / `How to apply` / `Source` / `Verified`) → **preserve the `Affirmed` line verbatim.** Never re-derive it, never re-date it, never drop it. Dropping it silently re-surfaces a node the user already affirmed, turning a durable decision back into a recurring prompt.
   - **You change a node's `Support-set`** — add a pointer, remove one, or re-point one (item 3) → **drop the `Affirmed` line.** The affirmation was made on a set of facts that no longer holds. This named step (items 1-3) is the **single place** a `Support-set` can change, which is exactly why the affirmation needs no date comparison and no staleness procedure: it is dropped **at the event**.

3. **Support-set referential integrity**: reconcile node `Support-set` pointers. **A node pointer carries no state** — no marker, no removal class, no date. The sweep does not *remember* that a target is gone; it **looks**, fresh, on every sweep. Full rule and rationale: `shared/skills/qdream/memory-rules.md § Higher-Order Tier` ("Support-set referential integrity") — follow the execution list below rather than re-deriving the reasoning here.

   **Execution list.** The normative order is `shared/skills/qdream/memory-rules.md § The reconciliation pass — three steps, and the order is normative`; execute it as the five items below. Item 1 is its Step 1 (re-point), items 2 and 3 are its Step 2 (resolve), and items 4 and 5 are its Step 3 (the ungrounded trigger and the Report).

   1. **Re-point.** Rewrite every node pointer whose target this sweep **renamed** (a `memedit` `replace` op on the node), using the `old target → new target` pairs in the **planned map** (`sweep/planned-map.json`, the queued renames of § SYN-WRITE and § SYN-STALE, and `handoff/working-map-seed.json`'s landed pairs from § ORI-RECOVER) that **those steps** recorded (the *crash-recovery* step, the *aggregate-memory-proposals* step, and the *process-stale-entries* step — **not** items 1 and 2 of this named step). `dream-write.py memedit` makes every record. § SYN-PROMOTE records removals only. Later in Phase 5, § APP-ADJUDICATE's `replace` ops that change a heading are journalled as renames too, but they run after this pass, so this sweep re-points no pointer onto them. At the next sweep such a pointer can resolve `confirmed-absent`, and its node then reaches the user-gated `Keep node / Remove node / Defer` prompt, never an autonomous removal. **This runs before resolving.** A rename changes a heading **without removing the entry** (for example § SYN-STALE's salvage-rewrite or a dedup merge that kept the entry under the other heading; the list is not exhaustive), so a renamed target still *exists* — an un-re-pointed pointer would resolve `confirmed-absent` and drive a node with fully intact ground to the deletion gate. The sweep holds the mapping it just created: this is the one case with perfect information.
   2. **Resolve.** For each remaining node pointer, look its target up **in an artifact this sweep actually loaded**, read together with the planned map: memory files on disk do not yet hold queued writes, so a target a queued op renamed to this heading is `resolved`, and a target a queued op removes is `confirmed-absent`. Do not guess, and do not infer from what you removed — the working map's removal half never decides an outcome (it only *names a cause*, below).
   3. **Classify.** Assign each pointer exactly one of three outcomes:
      - **`resolved`** — the target exists now.
      - **`confirmed-absent`** — the sweep **could look** and the target is **not there**: its artifact was loaded/analyzed *this sweep*, and the exact heading is absent from it.
      - **`indeterminate`** — the sweep **could not look**. Covers: a `project memory (<project-path-key>)` pointer whose project was **not analyzed this sweep** (or is inaccessible, or whose path key is absent from `.dream-state.json` `projects`); a `<plan-slug> § <section>` pointer whose project file the sweep cannot open, which is ambiguous across projects, or whose slug **could exist in a project not analyzed this sweep** (a plan-slug carries no project qualifier, so an absence is not verifiable across all projects); **every** `session <session-id>` pointer (session transcripts are not verified during reconciliation, and no phase agent or orchestrator opens one — Rule 7); a pointer in an **unrecognized or illegal form** (never guess what a malformed pointer meant, even when a near-match target exists); and any target the sweep otherwise cannot reach. **Never** treat an `indeterminate` pointer as absent.

      "Analyzed this sweep" in this list is wider than § SYN-OUTCOME's "read by an agent": a project counts when a dispatch ran Task 4 on its memory file (`all tasks` or `Tasks 4-5 only`), and its headings are its side file's `entries[]`. A quiet project's pointers are `indeterminate`. A `user memory § <heading>` pointer is looked up in the config repo's `memory/MEMORY.md` and in the manifest's `user_memory.json` entries, which list every `memory/topics/*.md` heading; it is `confirmed-absent` only when neither holds the heading.

      An `episodic_ledger #<N>` pointer with `<N>` in range **always resolves** — the ledger is append-only and its records are never removed.

      **`confirmed-absent` means the sweep looked and it was gone. `indeterminate` means the sweep could not look.** Conflating them drives a node to the deletion gate on evidence the sweep never actually had. Same principle as the unreachable-provenance rule (`shared/skills/qdream/memory-rules.md § Type Taxonomy`): an anchor that cannot be opened is not evidence the claim is false.
   4. **Trigger.** A node is **ungrounded** — and surfaced at the Phase-4b gate — **if and only if it has at least one pointer and EVERY pointer is `confirmed-absent`**: zero `resolved`, **zero `indeterminate`**. **Any single `indeterminate` pointer blocks the gate** — the sweep cannot claim a node has lost all its ground when there is ground it never checked. This **fails safe**: keep the node. (regression fixtures: transition-fixtures.md FIX-SUPPORTSET-*)
   5. **Report.** **Name every `confirmed-absent` and every `indeterminate` pointer, together with the node carrying it** (`sweep-decide-apply.md § Report`). Neither is ever removed and neither removes its node on its own, so the Report is the only thing that keeps them visible.

   - **Ledger pointers are exempt — they are history, not live references.** The `support_set` arrays on `episodic_ledger` records are **never reconciled**: never resolved, never re-pointed, and their records **never rewritten** (§ SYN-HIGHERORDER item 1, append to the ledger: *append-only — never rewrite prior records*). A ledger pointer whose target no longer exists is **not a defect**; it records what the episode named at the time. (The live ledger already carries one: record 3's pointer names an entry a later sweep rewrote under a new heading. **Leave it** — rewriting it would violate append-only.) Everything above governs **node** pointers only.
   - **A dedup merge removes nothing — there is no `merge-absorption` removal class.** `shared/skills/qdream/memory-rules.md § Merge Strategy` merges a *new proposal* into an *existing entry*; it **never removes an existing entry**, so it can never orphan a pointer's target. The one thing it can change is the surviving entry's *heading* — and that is a **rename**, resolved by the execution list's **item 1 re-point** (from the working map's `old target → new target` pairs), never a removal.
   - **Retirement is not a Support-set removal.** Pointers never name governance sections, so a rule retired by the Phase-4b retirement pass is not a Support-set target and can never move a node toward removal. **Node removal is sweep-only and user-gated** — the read-time provenance auto-demotion licence (`shared/skills/qdream/memory-rules.md § Type Taxonomy`) applies to base `memory/MEMORY.md` entries, **never** to a higher-order node; the sole node-removal path is the user-gated Phase-4b prompt (`sweep-decide-apply.md § DEC-GATE`).
