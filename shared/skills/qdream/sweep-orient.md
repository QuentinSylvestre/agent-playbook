# qdream sweep — Phase 1: Orient

Part of the `/qdream` skill: `SKILL.md` in this directory loads this file at the start of a full sweep (its phase index), after `sweep-handoff.md`. The Rules and destructive-path invariants in `SKILL.md` apply here. Orient runs in the orchestrator, in the order `sweep-handoff.md § Orient order` states; the steps below give each step's rule.

### Phase 1 — Orient

1. **Resolve paths**:
   - Config repo: per `shared/AGENTS.md § Config Repo Locations` (the `root=` value of `~/.agent-playbook/config`; `store-resolver.py paths` prints it)
   - Provider session sources: enumerate providers by globbing `providers/*/steering/memory-sources.md` **and** `providers/*/steering/*/memory-sources.md` (one subdirectory level deep) relative to config repo. Each match is one provider. Read each file for session locations and formats. If no matches found, skip session analysis gracefully (plans/done and memory verification still run).

2. **Read state file** `[ORI-STATE]` (`memory/.dream-state.json` in config repo):
   ```json
   {
     "schema_version": 3,
     "last_run": "ISO-8601",
     "projects": {
       "<path>": { "last_analyzed": "ISO-8601" }
     },
     "rejected_lessons": [],
     "outcome_tags": [],
     "episodic_ledger": [],
     "cost_records": [],
     "model_routing": {},
     "deferred_sessions": {},
     "quiet_sweeps": {}
   }
   ```
   `§ ORI-STATE` reads the state file and the journal and writes nothing. **Schema-version handling** (canonical v3 shape: `shared/skills/qdream/memory-rules.md § State File Format`):
   - **File exists, `schema_version: 3`**: use as-is.
   - **File exists, `schema_version: 2` or `1`**: `<python> <skill-dir>/scripts/dream-write.py state migrate --snapshot-sha <sha>` migrates it after `dirty` (`sweep-handoff.md § Orient order`, step 7). The migration is additive: v2 gains `cost_records: []`, `model_routing: {}`, `deferred_sessions: {}` and `quiet_sweeps: {}`; v1 also gains `rejected_lessons`, `outcome_tags` and `episodic_ledger` as empty arrays; `schema_version` becomes `3`, and every existing section, `last_run` and `projects` included, is preserved unchanged (no backfill). The script validates the new file with `verify-dream-state` before it replaces the old one, so a FAIL leaves the file untouched: report it and stop.
   - **File does not exist (first run)**: nothing is written at Orient. The manifest reads a first run from the last config-repo commit (`baseline_rule: first_run_commit`), and `§ APP-STATE`'s `state apply` creates the file at `schema_version: 3`.

   Next comes the paused-sweep check (`sweep-handoff.md § Orient order`, step 2). Then the **Crash-recovery journal** step (`§ ORI-RECOVER`, full-sweep-only) runs, from `sweep-recovery.md` — loaded only when `memory/.dream-journal.jsonl` is non-empty and no paused sweep is resumed. Single-flight: `SKILL.md § Destructive-path invariants`.

3. **Discover projects** `[ORI-DISCOVER]`: discovery and session selection are done by the manifest script, never by hand. Run, from the config repo root (`<python>` and `<skill-dir>` as defined in `SKILL.md`):

   ```
   <python> <skill-dir>/scripts/dream-manifest.py manifest --state <config-repo>/memory/.dream-state.json --repo <config-repo> --exclude-session <this sweep's own session id>
   ```

   Pass `--exclude-session` when the harness exposes the running session's id (the provider's `memory-sources.md` says how); otherwise omit it and note in the Report that the sweep's own session may be listed. The script creates the work folder (`shared/AGENTS.md § Dream autonomy exception`), writes one stripped transcript per selected session (user and assistant text; a user turn is a typed prompt, an answer to a question the agent asked, labelled `[user:answer]`, or a message typed while the agent worked, labelled `[user:mid-turn]`, and all three count as user speech) plus `manifest.json` and its side files there, and prints one line per project, the totals, the `sweep due:` line and the path of `manifest.json`. The work folder sits outside the config repo and OneDrive-synced folders (measured 2026-09-24 on the user's Windows machine). Read `manifest.json` whole; read side files only where a step names them. Exit codes (`dream-manifest.py --help`):
   - **0** — at once run `<python> <skill-dir>/scripts/dream-sweep.py dirty --repo <config-repo>` and hold the `snapshot sha256` and the `guard digest` it prints for the whole sweep; then write the `§ ORI-RECOVER` results and run `state migrate` when needed (`sweep-handoff.md § Orient order`, steps 5-7); then continue with the confirm list (step 4).
   - **5 — leftover work folder.** A folder from an earlier run exists; the script prints its `snapshot_at`. A folder holding `handoff/progress-*.json` is a paused sweep, already offered before `§ ORI-RECOVER` (`sweep-handoff.md § Orient order`, step 2). For any other folder, offer resume only when the folder's `manifest.json` parses (the printed `snapshot_at` is not `unknown`); otherwise offer only discard or stop. Ask the user: **resume** — use the existing `manifest.json` as it is, with its own `snapshot_at` (same snapshot only; never rerun `manifest` into it, never mix it with a new snapshot), reusing an existing `sweep/dirty-at-orient.json`, `sweep/backup/` and `sweep/dispatch.json` rather than running `dirty` or `dispatch` again; **discard** — run `<python> <skill-dir>/scripts/dream-manifest.py clean`, then rerun the command above; **stop** — end the sweep and leave the folder, naming its path. Stop is the answer when the user gives no clear choice, and always when the user indicates another sweep may be running (`SKILL.md § Destructive-path invariants`, single-flight). Never delete, empty or reuse the folder any other way.
   - **2 or 3** — usage error or guard refusal: report the printed message and stop the sweep; do not ask, do not retry with other paths.
   - The venv is missing, or a script exits 2 with `guard did not run: venv missing`: stop with the message in `SKILL.md § Interpreter`.

   The script implements the three discovery methods below (merged and deduplicated by normalized path, plus `--add` paths and the state file's own projects) and each provider's selection rule; they are defined here so the rule and the script can be checked against each other:

   **A. Session-based discovery**: For each provider session source, scan session metadata for unique workspace paths (the `cwd` field). Include ALL sessions (both user-initiated and sub-agent) for project discovery purposes — a project exists regardless of how it was worked on. Use the per-project `last_analyzed` timestamp (or the temporal baseline for unknown projects) to filter sessions temporally. A path inside `<project>/.claude/worktrees/` (a Claude Code sub-agent worktree copy) is not a project: its sessions count toward `<project>`, and the manifest's `errors[]` names the copy.

   **B. Structural discovery**: For each parent path found in (A), recursively scan for `memory/MEMORY.md` or `AGENTS.md` files. Any directory containing either file is a project. This catches sub-projects that are only ever opened as sub-agents of a parent directory, or that were worked on in Kiro IDE without a matching CLI session `cwd`. **Never walk into the store repo** (`~/.agent-playbook/stores`), and a session `cwd` at or inside it is not a project. A store directory holds *another* workspace's memory and project files, so scanning it discovers the store itself as a project — with its own memory file and its own sweep entry. Store-backed workspaces are discovered by (C) instead, under their real path.

      **C. Store discovery**: read every store's `STORE` file through the store resolver (`dream-manifest.py` calls its `scan_stores`). The **contents** of `STORE` name the project; the directory name never does (`shared/skills/qdream/memory-rules.md § Workspace Store`). A `local` store whose folder exists is merged into the discovered set under that folder, exactly as (A) and (B) merge theirs, so a store-backed workspace is analyzed under its own path even when it has no session in the window. A store that no discovered project resolves to is a store-only project keyed `store:<identity>`. An unreadable store repo is reported in `errors[]`, and no store-only project is listed that run. This step is the `STORE` file's consumer per `shared/AGENTS.md § Structure Requires a Consumer` — a type-3 consolidation-sweep consumer, read on every full sweep. (regression fixture: transition-fixtures.md FIX-DISCOVER-store-not-a-project)  **Guard against subdirectory-as-project false positives**: Method A treats a session's literal `cwd` as project identity with no independent check. When a discovered path carries **zero** of its own project markers (no `memory/MEMORY.md`, no `AGENTS.md`, no `plans/`) **and** a parent directory — walking up — **does** carry them (Method B's own markers), flag the path in the confirm list (Confirm project list, below) as a likely subdirectory of that already-known project (a monorepo leaf, an archive folder that happened to be a command's `cwd`) rather than silently finalizing it as independent. Left unflagged, this produces a structurally-guaranteed-empty dispatch every sweep in perpetuity: no markers of its own to classify or drift-check, and no session content beyond the one that created the spurious entry. The manifest reports such a path with `subdirectory_of: <that project>`; flag every project whose `subdirectory_of` is set. The config repo's `shared/` and `providers/` never count as that parent: `shared/AGENTS.md` is the deployed global file, so a skill folder reports the config repo itself.

   **Session selection for dispatch** (distinct from discovery): the manifest applies each provider's rule in its `memory-sources.md` — which records are genuine user speech, how sub-agent transcripts are told apart, per-record recency against the project's baseline, and the `deferred` and `history_only` kinds — and excludes the running sweep's own session (`--exclude-session`). Each project's `sessions[]` is the session list; do not re-filter it. Empty sessions (created, never used) are counted in `empty_sessions`, never listed and never dispatched. Retired format: the kiro-cli v2 `parent_session_id` discriminator no longer applies (v3 has no such field; `providers/kiro/steering/memory-sources.md`).

   **Collapse Kiro IDE checkpoint duplicates.** Kiro IDE writes a second session file for one logical session, titled `<original title> (checkpoint)`, whose user-turn sequence is a strict prefix of the original's. The manifest does not collapse these, and the orchestrator never reads session files to find them (Rule 7): both files are dispatched as listed. The detector is the project's per-project sub-agent: it compares user-turn text sequences (a strict prefix; the ` (checkpoint)` title suffix is a corroborating signal, not the test), analyzes only the longest of each prefix-chain and reports the collapsed pairs, whose count the Report carries. Left uncollapsed these inflate every session count and therefore every `frequency` value derived from IDE sources, plus the work-volume arm of the `shared/skills/qdream/memory-rules.md § Staleness nudge`.

   **Claude Code fork duplicates are collapsed by the manifest.** A fork or background handoff writes a new transcript carrying the whole earlier history under the same record uuids. Within each project's selected transcripts (resolved per file), the script keeps each shared record once, in the transcript with the most records; a transcript with no unshared conversation turn is left out of `sessions[]` and named in its project's `fork_collapsed` (`dropped`, `kept`, `shared_records`), and a transcript that shares only a prefix keeps its own turns, its `boundary` moved to its first unshared conversation turn. A transcript whose keeper is outside the project's selected transcripts is kept and named in that project's `errors[]`. The rule: `providers/claude/steering/memory-sources.md § Forks and background handoffs`. Show `fork_collapsed` on the confirm list beside the session counts; nothing else in the sweep acts on it.

4. **Confirm project list**: Present the discovered project list to the user for confirmation, grouped by the manifest's per-project `status`.
   - **Known projects** (`status: known`, already in `.dream-state.json`): listed as auto-included, no confirmation needed.
   - **New projects** (`status: new`, not in state file): listed separately, user confirms which to include. A declined new project, including a declined likely subdirectory, is never written to the state file, so the next sweep offers it again as new.
   - **Removed projects** (`status: removed`, in state file but path no longer exists or no longer has project markers): listed for user acknowledgment before removing from state (under the project's `state_key` when the manifest carries one). A state entry naming a Claude Code worktree copy is listed here too; acknowledging it deletes only that key.
   - **Likely subdirectories** (`subdirectory_of` set): flagged with the parent project, per the guard above.

   For every project show: its `status`; its sessions by kind — new (`kind: normal`), `deferred`, `history_only` — and how many have `boundary: unknown` (read whole); `older_sessions_not_read` and `empty_sessions`; `due` (its oldest unread transcript nears the provider's deletion age — sweep it now or lose turns); `baseline_rule` (`state`, `last_run`, `first_run_commit` or `full`); and every line of its `errors[]`, verbatim. Above the list show the top-level `new_project_baseline` (`rule` and `since` — new projects are read only from that time), `sweep_due`, the top-level `errors[]` verbatim, and `empty_sessions` for sessions naming no workspace. A project's errors never hide it: it stays on the list with its errors beside it. When an error names a transcript or session the script could not read (an `unreadable <transcript>` line, or a Kiro session that shows activity but was `not read`), say beside it that the project will not be stamped this sweep (`sweep-decide-apply.md § APP-STATE`).

   Wait for user confirmation before proceeding. User may add paths manually or exclude projects. **Reruns**: a manual addition (`--add <path>`) or a whole-history read for a project whose older sessions were not read (`--full <path>`, offered for every project with `older_sessions_not_read` above zero) needs a new manifest. The work folder now exists, so a plain rerun exits 5: run `clean`, then rerun `manifest` with every flag of the previous run plus the new `--add`/`--full` flags (each repeatable), and show the new list. The rerun's `snapshot_at` replaces the old one; stamping uses the manifest the sweep finally runs on.

   **Choose dispatch models** `[ORI-ROUTE]` (full sweep only): after the list is confirmed, show each role this sweep dispatches — `task4` (the per-project sub-agent of `sweep-gather.md § Phase 2 — Gather (parallel sub-agents)`: it reads sessions and classifies memory entries against governance) and `verifier` (the Cross-validation gate) — and `drafter` (the read-only agent that writes each governance proposal's exact text before the gate, `sweep-decide-apply.md § DEC-PROPOSALS`), each with its model. Show `model_routing[<provider>]` from the state file when it exists (with its `confirmed` date); otherwise recommend the orchestrator's own model for `task4` and `verifier` — judgment roles on a cheaper model give shallow classifications and weak refutations — and Sonnet for `drafter`, which copies and drafts text rather than judging (a stored routing without `drafter` gets the same recommendation for it). Phase agents are not a role here: they run on the orchestrator's own model (`sweep-handoff.md § Dream Phase Agent Brief`). `<provider>` is the harness running this sweep, named as the manifest names providers (`claude`, `kiro`); concrete model names are in that provider's steering file (Claude Code: `providers/claude/steering/memory-sources.md § Dispatch model routing`; Kiro: its overlay of this file). Where the harness offers no per-dispatch choice, every role runs on the orchestrator's model: say so and record that. The user confirms or changes each role; `orient.json` carries the choice (`§ ORI-DISPATCH`) to `sweep-decide-apply.md § APP-STATE`, which writes it to `model_routing[<provider>]` with `confirmed` set to today. Dispatch each role on its confirmed model.

5. **Read user memory** `[ORI-READMEM]` (`memory/MEMORY.md` in config repo). Note existing entries for dedup in Phase 3. **Also read the higher-order tier** (`memory/HIGHER_ORDER.md` in config repo) if it exists: its nodes are prior-sweep abstractions carrying `Support-set` pointers (`shared/skills/qdream/memory-rules.md § Higher-Order Tier`). Note them — they **re-enter this sweep's reflection input** and are the compounding substrate the Phase-3 higher-order synthesis step updates. **Also read `memory/topics/improvement-signals.md`** (config repo) if it exists: it holds the user-scope `[improvement_signal]` entries that § SYN-PROMOTE increments, re-evaluates and promotes (`shared/skills/qdream/memory-rules.md § [improvement_signal] sub-form`). The other `memory/topics/*.md` files are not read here: the headings of their entries in the manifest's `user_memory.json` are the count-verify basis for a topic-file dispatch (`sweep-synthesize.md § SYN-RECONCILE`).

6. **Build dispatch list** `[ORI-DISPATCH]`: write `handoff/orient.json` with `<python> <skill-dir>/scripts/dream-sweep.py orient --snapshot-sha <sha> --provider <name> --model <role>=<model>... [--project <path>]... [--recover-line <text>]...` (the confirmed projects and the confirmed model per role as arguments; the script fills the rest and `orchestrator_sessions` from `CLAUDE_CODE_SESSION_ID`; keys: `sweep-handoff.md § Handoff files`), never by hand, check it with `<python> <skill-dir>/scripts/dream-sweep.py handoff check orient.json`, then run `<python> <skill-dir>/scripts/dream-sweep.py dispatch --confirmed orient.json --snapshot-sha <sha>`. The script builds `sweep/dispatch.json` and one input file per agent by the rules below, stated here so the rules and the script can be checked against each other; never build the list by hand. It maps each confirmed project path to its manifest `sessions[]` — every kind (`normal`, `deferred`, `history_only`). The existing per-project sub-agent receives, as its session file paths, each session's `source` (the original transcript) and its stripped file (`stripped`, relative to the work folder; `null` when the script could not write it — then only `source`), with the session's `kind` and `boundary` (`L<n>` where the new turns begin, or `unknown`: read the whole session), and as its temporal baseline the project's `last_analyzed`, or the manifest's `new_project_baseline.since` for a new project (none under `baseline_rule: full`). A `history_only` session has no transcript: its stripped file holds the `history.jsonl` prompt text, and the sub-agent discloses the coverage gap. `dispatch.json` records which sessions went to which agent: `dream-sweep.py coverage` stamps a project only when every listed `normal` session comes back in the `sessions_read` of the agent it went to (`sweep-decide-apply.md § APP-STATE`). **Each project's archive location is resolved before the signal test**: the manifest reads the project's `AGENTS.md`/`CLAUDE.md` for a governed plan-archive path (its side file's `plans.archive`) and falls back to `plans/done/` only when governance is silent. This is the same resolution `/qclose` § Step 4 ("use the project-governed archive location") and `/qplan`'s Governance gate already perform — qdream was the outlier, and a project archiving elsewhere (e.g. `docs/records/plans/done/`) had its entire archive reported as "no archive found" on every sweep.

   **Choose each confirmed project's dispatch** (the quiet-project cadence; `memory_pass`, `memory_flags` and `quiet_sweeps` are per project in `manifest.json`, the entries' flags in its side file). Take the first rule that applies:
   - At least one session in `sessions[]`, or a non-empty `plans.new_plans` in its side file → the per-project sub-agent with `{task_scope}` = `all tasks`. When the project's listed sessions exceed the chunk budget (`dispatch --chunk-bytes`, default 450,000 stripped bytes), it is split instead: one `Tasks 4-5 only` agent when it has a memory file, and N `sessions only` agents, sessions packed in manifest order, a session over the budget alone in its chunk, the plan-archive task in chunk 1 (`sweep-gather.md`, the brief's Scope).
   - A `memory_file` whose `memory_pass` is `flagged` or `periodic` → the per-project sub-agent with `Tasks 4-5 only` and an empty session list. First read the project's `errors[]`: when a line reads `unreadable memory file <path>`, the manifest saw none of its entries and its `memory_pass` rests on the counter alone. Report that line beside the project and dispatch nothing for it; its file is verified once it can be read.
   - Otherwise → no agent this sweep: a quiet project. It is not stamped (`sweep-decide-apply.md § APP-STATE`, reason `quiet`), and the Gather phase agent still runs its harness harvest (`sweep-gather.md`, § GAT-PLANS harvest). A project with no sessions, no new plans, no memory file and no archive has nothing to harvest either and is skipped.

   `memory_pass` is `flagged` only when an entry has `stale_after_passed`, `stale_when_fired` or a non-terminal `Governance-conflict` (`governance_conflict_open`). Every other flag (`cited_paths_missing`, `cited_slugs_missing`, `cited_path_changed`, `cited_commit_missing`, `stale_when_unknown`) never dispatches anything by itself: it goes to a dispatched agent as an input, and a quiet file's flags are checked at its periodic pass. Every dispatch, `all tasks` included, receives each entry's flags and its `suspect` value. A suspect is an input that selects the entry for a full check, never evidence of staleness; `stale_when_unknown` is informational and never makes a suspect (`shared/skills/qdream/memory-rules.md § Suspect memory entries`).

   **User memory** follows the same cadence from the manifest's `user_memory` block, one dispatch per file (`sweep-gather.md § Phase 2 — Gather (parallel sub-agents)`): `periodic` → one `Tasks 4-5 only` dispatch for each file in `user_memory.json`'s `files`; `flagged` with the block's `quiet_sweeps` at 4 or more → one for each file, as for `periodic`, so a sticky flag cannot starve the other files of their periodic pass and the counter can reset (`sweep-decide-apply.md § APP-STATE`); `flagged` otherwise → one for each file whose `file_flags` hold `stale_after_passed`, `stale_when_fired` or `governance_conflict_open`, never for a file whose flags hold none of those three; null → none. A file named in a top-level `unreadable memory file <path>` error is reported, not dispatched. (regression fixtures: transition-fixtures.md FIX-DISPATCH-quiet, FIX-DISPATCH-user-memory-flagged)

   If no provider steering files are found at all (neither `providers/*/steering/memory-sources.md` nor `providers/*/steering/*/memory-sources.md` matches), skip session discovery gracefully and note "No provider session sources found" in the Report — dream can still operate on projects with existing memory or `plans/done/`.
