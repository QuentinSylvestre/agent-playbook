# qdream sweep — Phase 2: Gather

Part of the `/qdream` skill: `SKILL.md` in this directory loads this file when Phase 2 starts (its phase index). The Rules and destructive-path invariants in `SKILL.md` apply here.

### Phase 2 — Gather (parallel sub-agents)

This phase runs in the Gather phase agent (`sweep-handoff.md`, its brief and its § Phases row). It reads `handoff/orient.json` and `sweep/dispatch.json` and ends by writing `handoff/gather.json` and `handoff/harvest.json`.

**Dispatch** (full sweep only): one sub-agent per entry of the dispatch list (`sweep-orient.md § ORI-DISPATCH`), on the `task4` model confirmed at `sweep-orient.md § ORI-ROUTE`. Render the briefs with `<python> <skill-dir>/scripts/dream-sweep.py brief --kind task4` (it fills the brief below from each agent's input file, with `{task_scope}` = `all tasks`, `Tasks 4-5 only` or `sessions only` as the list says, and puts the inputs in a data file the brief names), then launch each agent with the exact prompt line `brief` printed, at most 5 per batch, one message per batch. A user-memory dispatch covers one file: `{project_path}` is `user memory`, `{memory_file}` is that file (`memory/MEMORY.md` or one `memory/topics/*.md` file named in the manifest's `user_memory.json`), and its plan archive is the config repo's `plans/done/`. A project with no entry on the list gets no agent this sweep; the phase agent still runs its harness harvest (§ GAT-PLANS, below the brief).

Each sub-agent receives this brief:

> **Dream Sub-agent Brief**
>
> You are analyzing project `{project_path}` for the `/qdream` skill. You are read-only, run no scripts, and may not dispatch further sub-agents (`shared/AGENTS.md § Dream autonomy exception`): read, search and list files only, with Read, Grep and Glob, never Bash or PowerShell, even to read a file; do NOT modify or create any file and do NOT write to memory. Return findings only, as your final message, using the Dream Sub-agent Return Schema below.
>
> **Tools and budget**: your tools are `Read`, `Grep` and `Glob`; your budget is about 120 tool calls. Your task ends when you return the JSON. If the budget runs out first, return the JSON anyway, partial, with `notes` naming the gap; never keep probing.
>
> **Scope for this dispatch**: {task_scope}. `all tasks` means Tasks 1-7 below. `Tasks 4-5 only` means: your session list is empty; run Task 4 (`GAT-CLASSIFY`) and Task 5 (`GAT-DRIFT`) in full and nothing else; return `unrelated`, `not_a_conflict`, `subsumed_entries`, `stale_entries`, `governance_conflicts`, `verified`, `task4_status`, `project_accessible`, `error`, `notes` and `sessions_unreadable`, with every other array empty, `sessions_read` empty and `checkpoint_collapsed` 0. `sessions only` means: you hold one chunk of a large project's sessions, and another agent runs Tasks 4-5 on its memory file; run Tasks 1, 2 and 6 over your session list, and Tasks 3 (`GAT-PLANS`) and 7 (`GAT-NATIVE`) only when your inputs file's `plans_task` is true (chunk 1); leave `unrelated`, `not_a_conflict`, `subsumed_entries`, `stale_entries`, `governance_conflicts` and `verified` empty and return `task4_status` as `skipped-context-budget` (count-verify ignores it for this scope).
>
> **Inputs provided**: project path, the memory file `{memory_file}`, the plan archive path (where Task 4's `plans/done/` checks look), temporal baseline (ISO-8601), user memory summary (headings only), the session list, and each memory entry's manifest flags: `stale_after_passed`, `governance_conflict_open` (the entry's non-terminal `Governance-conflict` states), `cited_paths_missing` and `cited_slugs_missing` (the cited paths and plan slugs the manifest script could not find), `cited_path_changed` (files cited on the entry's `Source` line committed after its `Verified` date), `cited_commit_missing` (cited commit hashes no known repository holds), `stale_when_fired` and `stale_when_unknown` (a `Stale-when: <tool> version > <x.y>` condition that fired or could not be read), and `suspect` (any of these flags but `governance_conflict_open` and `stale_when_unknown`). A manifest flag tells you where to look first, never what to conclude: confirm a missing path or slug yourself before you quote it as a failing check (a path may be relative to another root), and evaluate `Stale-after` yourself. A `stale_when_unknown` condition is not fired: it forces nothing. Give every `suspect` entry its full type-specific verification and list it in `verified`; a suspect whose check passes is not stale (`shared/skills/qdream/memory-rules.md § Suspect memory entries`). Each session has an id, a `kind` and a `boundary`, plus two paths: `source` (the original transcript) and `stripped` (a decoded copy holding only user and assistant text; absent when it could not be written, then read `source`). Read the stripped file when you have it. A user turn in it is a `[user]` line (a typed prompt), a `[user:answer]` line (the user's answer to a question the agent asked, one `Q: <question> → A: <answer>` line per question; the `Q:` half is the agent's words, so quote the `A:` half) or a `[user:mid-turn]` line (a message the user typed while the agent was working). All three are user speech. In it, the new turns begin after the `=== NEW TURNS BEGIN ===` marker; earlier turns are context only. `boundary` names the line where the new turns begin, or `unknown`: read the whole session. `kind` is `normal`, `deferred` (still in progress; read it like the others) or `history_only` (no transcript: only the user's prompt text, no assistant turns — say so beside any finding drawn from it). Return in `sessions_read` the id of every session you actually read to its end; leave out any session you skipped or read only in part.
>
> **Kiro IDE checkpoint duplicates**: Kiro IDE can write a second session file for one logical session, titled `<original title> (checkpoint)`, whose user-turn sequence is a strict prefix of the original's. Detect such a pair by comparing the user-turn text sequences (a strict prefix is the test; the ` (checkpoint)` title suffix, where you can see it, only corroborates). Analyze only the longest session of each prefix chain, list each dropped duplicate in `sessions_read` once the longest one is read to its end, and return the number dropped in `checkpoint_collapsed`. Uncollapsed duplicates inflate every session count and every `frequency`.
>
> **Tasks** (ordered by signal value — prioritize top tasks under context pressure):
>
> **Evidence grounding (applies to every task below)**: every `improvement_signal` and `memory_proposal` you emit — from ANY task, including the `GAT-PLANS` `plans/done/` scan — MUST carry a verbatim `evidence_quote`: the exact span (session line or plan text) that grounds the claim, copied word-for-word, not paraphrased. The quote is the load-bearing evidence; the `observation`/`why` prose is secondary and must be entailed by it. Quotes preserve the source's original spelling and typos verbatim — silent corrections break grep-based re-verification. The one permitted content alteration is a `[redacted]`/`[uuid]`-style placeholder over a secret or volatile identifier; a redacted quote is matched by grep on its unredacted neighbours (`shared/skills/qdream/memory-rules.md § Exclusion List`, "Sanitize quoted material"). Before emitting any item, re-open its `source` anchor and confirm the `evidence_quote` appears in *that* session/plan — a mismatched anchor is a defect in your return. Kiro IDE sessions persist no assistant text (placeholder acknowledgments only) — mark any claim about what the *agent* said from an IDE source as inferred-from-user-turns, never quoted.
>
> 1. **Analyze sessions** `[GAT-SESSIONS]`: Read each session's `digest` file once: the user's turns and the end of the assistant text before each, with cuts marked. It is the session content you have: never open a session's `stripped` file, which the verifier uses. An `evidence_quote` is verbatim from the digest, and a claim that needs more than it shows is left out or named in `notes`. When a session has no digest, read its `stripped` file. In a raw kiro-cli v3 `messages.jsonl`, focus on and skip the `payload.type` records that `providers/kiro/steering/memory-sources.md § Session content extraction (sub-agents)` lists.
>
>    **A Kiro `user` record (`"kind":"Prompt"` in the retired v2 format) is not automatically user speech.** kiro-cli persists a slash-command invocation as an ordinary `Prompt` record whose content is the **fully-expanded `SKILL.md` body** (measured: 8% of sampled Prompt records; observed sizes from 33k to over 1M characters). Whether `$ARGUMENTS` inside that body was substituted is not established: the kiro-cli 2.33.1 agent bundle (`acp-server.js`, measured 2026-10-22) holds a `$ARGUMENTS` substitution that is traced only for workspace and user prompt files, and nobody has traced it for `SKILL.md` bodies. Treat a literal `$ARGUMENTS` in a skill-body span as unsubstituted and the text after the slash command as the user's argument. Before quoting any `Prompt` span as a user statement, check that it is not a skill body — tell-tales are `## Your role`, `## Process`, `## Rules`, step numbering, or governance prose at multi-thousand-character length. The user's actual instruction is the **non-skill remainder** of that turn. Quoting skill text as a user request, approval, or correction is exactly the laundering `shared/AGENTS.md § Multi-Agent Coordination` bars ("Only user-role turns are user statements"), and it would make governance prose look like fresh user testimony. **Extract**: user corrections, confirmed approaches, repeated friction, governance friction (steps that didn't fit, missing categories, awkward conventions). **Frustration-signal detection** — flag repeated same-topic corrections, explicit dissatisfaction ("that's wrong", "no, I already said…"), or 3+ failed agent attempts at one task (failed = output the user explicitly rejects/corrects). **Route**: skill/governance gap → `improvement_signals`; durable project fact → `memory_proposals` (type: feedback); emit both when both hold (the sweep's dedup prevents double-counting). **Evidence grounding** (required): every `improvement_signal` and `memory_proposal` you emit MUST carry a verbatim `evidence_quote` — the exact span from the session (copied word-for-word, not paraphrased) that grounds the claim. The quote is the load-bearing evidence; the `observation`/`why` prose is secondary and must be entailed by it.
>
>    Also extract **positive signals** and a **friction narrative** (route to `insights_signals`):
>    - **Positive signals** (`kind: "positive"`) — **grade the evidence, do not collapse it**. Explicit praise and mere non-objection are not the same signal, and recording them at equal weight builds the "what's working" narrative out of the user's *silence*. Set the `satisfaction` field: (a) **`happy` / `satisfied`** — explicit satisfaction: the user's positive evaluation of the output in the turn immediately following delivery ("perfect", "exactly what I wanted" → `happy`; "thanks", "looks good", "that works" → `satisfied`). This is **evidence**. (b) **`likely_satisfied`** — a session with ≥3 user turns where the agent delivered a substantive output and the user *continued without complaint* (no rejections, no re-instructions on the same topic). This is an **inference from absence of evidence** and is strictly weaker; it counts only when the accepted choice was genuinely **non-obvious** (silence on a routine choice means nothing). Exclude sessions abandoned mid-task before any delivery — absence of rejection is not evidence of success. Record the active skill or governance rule in `attribution` (best-effort; if uncertain, attribute to the project generally).
>    - **Friction narrative** (`kind: "friction_narrative"`): produce only when ≥3 sessions are analyzed for this project — write a 1-2 sentence summary of the dominant friction pattern across this project's sessions (what recurs, what triggers it). Set its `frequency` to the count of this project's sessions exhibiting the pattern (so `SYN-INSIGHTS` can rank dominant patterns across projects). **Affect — the frustration/dissatisfaction sink**: when the pattern reflects explicit user dissatisfaction or frustration (the frustration signals flagged in the detection step above), set the narrative's `satisfaction` to `dissatisfied` (mild) or `frustrated` (strong); otherwise leave it `null`. This gives a detected frustration a documented sink. This is a UX-level summary for the Insights Report, distinct from `improvement_signals` (which captures actionable governance gaps).
>
> 2. **Match failure archetypes** `[GAT-ARCHETYPES]`: Read `shared/skills/qdream/failure-archetypes.md`. If the file is missing or empty, skip this task and put "failure-archetypes.md not found" in `notes` — do not error. For each archetype, scan session content for matching signals. Report matches with: archetype name, session evidence (quote the relevant exchange), affected skill/step, and frequency (how many sessions exhibit this pattern). Route matches per `shared/skills/qdream/failure-archetypes.md § Output Routing`. Also note any recurring pattern that does NOT match an existing archetype — include it as a "candidate archetype" with the same evidence structure.
> 3. **Scan the project's plan archive** `[GAT-PLANS]`: Read plans archived since temporal baseline. **The archive path is the one the orchestrator resolved for this project** (the governed path from the project's `AGENTS.md`, else `plans/done/`) — do not assume `plans/done/`. Extract: resolved decisions, feedback corrections, patterns discovered.
>
>    **Harness-opportunity harvest** (closes the learning-loop read side): scan each archived plan's `## Harness Improvement Opportunities` section. These hold friction observations captured during `/qexplore`/`/qplan`/`/qdev` and triaged at archive time by `/qclose` Pass 2 — items marked **Promote** were already applied to governance, but items marked **Accept and note** were recorded write-only and never resurface. Harvest the **Accept and note** (un-promoted) items: for each, route to `improvement_signals` with `target_file` inferred from the suggested change (default `shared/AGENTS.md` when unclear), `observation` carrying the friction + suggested change verbatim, and `frequency` set to the count of *distinct archived plans* raising a semantically equivalent concern (so one-off notes stay below the promotion gate while recurring friction crosses it), and `impact_assessment` set from the item's recorded `cost:` segment **when present** — re-derived from the observation when the segment is absent (older archived items lack the `cost:` segment, so re-derivation remains a live path; `shared/AGENTS.md § Harness Improvement Capture`). Tag the observation with the `HARNESS_HARVEST:` prefix so `SYN-PROMOTE` can recognize plan-recurrence-based frequency. Do not re-harvest items whose suggested change is already present in current governance (`shared/AGENTS.md`, `shared/skills/*/SKILL.md`, `shared/skills/*/TEMPLATES.md`, `shared/skills/qdream/sweep-*.md`) — that means it was effectively promoted; treat as resolved.
>
>    **Plan-cluster analysis**: if the project's archive directory exists — the project-file-class location `shared/skills/qdream/memory-rules.md § Resolution contract` returns, which is `plans/done/` in the workspace's store (in the workspace itself only for a no-create folder) — compare plan titles and Intent sections (not full bodies) across the archive to identify plan clusters — multiple plans targeting the same feature, area, or concern. Cap comparison to the 50 most recent plans by filename date prefix to bound context usage. Flag clusters where: (a) plans have overlapping scope or sequel relationships (one extends/fixes/refines another), OR (b) same-day plans with related scope suggest the required refinement wasn't captured in one pass. Sequel/ordering claims must be cross-checked against each plan's internal `Date:` header — archive filenames encode archival order, which can invert authoring order. For each cluster, note the plan filenames, the overlap, and whether later plans indicate missed intent from earlier ones. If the resolved archive path is absent, skip cluster analysis and note "no archive found" in the return. If the archive exists but holds no playbook-grammar plans (no `## Intent`, no `[P:N]`, no `## Harness Improvement Opportunities`), **say so explicitly** — a silently empty harvest reads as "nothing to harvest" when the truth is "archive is not in playbook format".
>
>    **Plan-efficiency signal**: also identify plans that delivered their intent in a single pass — no sequel plans, no same-area follow-ups, no scope-expansion plans within 14 days, AND the project had continued activity within that 14-day window (evidenced by sessions in that project after the plan). These represent effective intent capture and planning. Route to `insights_signals` with `kind: "positive"`, noting the plan filename in `evidence` and attributing to the skill/area that succeeded.
> 4. **Read/verify project memory, and classify every entry against governance (five-way — the four governance-relationship classes plus the separate `stale_entries` channel)** `[GAT-CLASSIFY]`: Read the memory file named in your dispatch (`{memory_file}`): for a project, its `memory/MEMORY.md` — the memory-class location `shared/skills/qdream/memory-rules.md § Resolution contract` returns, which is the workspace's store. If absent, note `project_accessible: true` and proceed (the sweep creates it in the store, never at the project root). For each existing entry, verify: patterns → grep codebase; decisions → check plans/done/ for reversal; feedback → check artifact still exists. For a `user memory` dispatch there is no project tree: a `pattern` entry is not grepped against any codebase, and its verification is the `Stale-after`, `Stale-when` and provenance checks only. So a `user memory` `pattern` entry whose `Stale-after` has passed, or whose `Stale-when` has fired, fails its verification: return it in `stale_entries` with that expiry quoted in `reason` and `expiry_fired: true`. The sweep never deletes a user-memory entry on your finding alone; it asks the user. **Then classify each entry's relationship to current governance** (`shared/AGENTS.md`, `shared/skills/*/SKILL.md`, `shared/skills/*/TEMPLATES.md`, `shared/skills/qdream/sweep-*.md`) into **exactly one of the four** governance-relationship classes below (`unrelated` / `not_a_conflict` / `subsumed_entries` / `governance_conflicts`), plus the **`task4_status`** return flag (a per-return *status*, not a per-entry class) recording whether you finished. The sweep **never asserts which artifact is more current** — a contradiction goes to the user undirected (`DEC-GATE`).
>    - **`unrelated`** — no governance rule is on point. **The modal case** (*"pytest needs `--no-header` on CI"* touches no rule). Return **the heading only** — no evidence, no quote. (Headings, not a bare count, are what let the sweep count-verify `task4_status: checked`.)
>    - **`not_a_conflict`** — the entry legitimately *narrows* a rule with a stated reason, or adds detail the rule does not cover — it is **not** a contradiction. Return the entry heading, the `governance_ref` (`<file § section>`), the narrowing reason, **and the verbatim governance span it narrows** (`governance_span`). This class is **routed through the Cross-validation verifier** like every other claim: free prose is the cheapest possible answer for a task that is *"the designated first casualty of context pressure"*, and a fabricated narrowing silently drops a real contradiction from the user's adjudication queue.
>    - **`subsumed_entries`** — current governance **already holds the entry's claim** (the entry has been absorbed and is a candidate for removal). Return the entry heading, the `governance_ref`, and a **normative** `subsuming_quote`: the verbatim rule span that absorbs the entry. It must be a span that *asserts* the claim — **never** an Exclusion-List row, a prohibited-command table entry, a non-goal, or a quoted counter-example (governance is full of verbatim spans stating what it *forbids*, and reading one as licensing a removal is a misjudgement). The verifier tests the entailment (Phase 3 Cross-validation gate), so quote the strongest normative span you can find.
>    - **`governance_conflicts`** — a genuine contradiction: the entry and a rule disagree. Return it here (with the rule it disagrees with, **the verbatim span of the contradicted rule** (`governance_span` — MUST emit), and the entry's `Verified` date) — but **do NOT flag a governance contradiction as stale**. A contradiction is *not* evidence the **entry** is wrong: the entry may **post-date** the rule and be the record of a correction the user made *after* it was written — in which case deleting it destroys the only evidence that governance has drifted. Which side is stale is a **user** decision (`DEC-GATE`), never a sub-agent judgment, and `stale_entries` is deleted autonomously (`SYN-STALE`) so routing a conflict there would destroy it. **Anti-heuristic**: a `feedback` entry's "the user corrected me" framing is **not** evidence it is newer than the rule — the rule may have been updated since. Compare dates; do not infer recency from tone.
>    - **`task4_status`** — `checked` when you classified **every** entry into exactly one of the four classes above, or `skipped-context-budget` when Task 4 was dropped or truncated under context pressure. **Never stamp `checked` after doing only the cheap half**: the sweep **count-verifies** it (the union of classified headings must equal the file's entry headings) and treats an incomplete union as `skipped-context-budget` regardless of your self-report, so a truncated return is caught mechanically.
>
>    **Task 4 classifies fresh; the sweep dedups.** Task 4 re-classifies **every** entry against current governance whenever it runs for the file, and does **not** try to skip entries already carrying a recorded `Governance-conflict` adjudication — it cannot reliably span-match a recorded quote, and it is *"the designated first casualty of context pressure."* So a settled `keep-entry` entry (still textually contradicting its rule) re-appears in `governance_conflicts`, and a settled `subsumption-kept` entry (still absorbed) re-appears in `subsumed_entries`, **by design, every sweep in which Task 4 runs for the file**. The **sweep reconciles** these fresh detections against the recorded adjudications at **`SYN-RECONCILE`** — the dedup lives there, not here.
>
>    **Precedence — `subsumed` beats `stale`.** An entry can be both stale (verification failed) and subsumed. Return it in **`subsumed_entries`**, not `stale_entries`: subsumed carries a normative quote and routes to a *user gate*, whereas `stale_entries` is deleted autonomously. And **each `stale_entries` item must quote its failing check in `reason`** — the grep pattern and paths, the missing-artifact path, or the reversing plan-slug — so the Cross-validation verifier can re-run it and return a per-item staleness verdict (Phase 3).
>
>    **Membership — the four classes are exhaustive; `stale_entries` is an additional channel, not a fifth class.** Every entry — stale or not — still gets exactly one of the four governance-relationship classes (`unrelated` / `not_a_conflict` / `subsumed_entries` / `governance_conflicts`); this is what makes the sweep's count-verify (union of the four class lists equals the file's entry headings) satisfiable. A merely-stale entry (verification failed, not subsumed) still needs its governance-relationship classification like any other entry — most commonly `unrelated` when no rule is on point. `stale_entries` sits alongside that classification as an additive annotation, never a substitute for it. The subsumed-beats-stale precedence above is unchanged: a stale-and-subsumed entry is classified `subsumed_entries` only.
>
>    **Provenance re-open & demotion**: for any entry carrying a re-openable `Source` anchor (`shared/skills/qdream/memory-rules.md § Memory File Format`), re-open the cited span (you are a sub-agent, so you open it — Rule-7-safe; no phase agent or orchestrator does). If it is **reachable AND contradicts** the entry's claim, return the entry in `stale_entries` (**demote**), quoting the contradicting span in `reason`. If the anchor is **unreachable** (session rotated / plan-slug absent), do NOT demote — the re-open is indeterminate; fall back to the type-specific verification rule above and judge the entry on that. Follow `§ Type Taxonomy` "Provenance re-open & auto-demotion".
>
>    **Skip licence and expiry**: the cheap mtime pre-filter may skip a semantic re-open **only** when the entry's `Verified` carries method **`anchor-reopen`** (`shared/skills/qdream/memory-rules.md § Memory File Format`); any other method, or an absent annotation, means you re-open. Independently, evaluate the entry's **`Stale-after`** (compare to today) and **`Stale-when`** (evaluate the condition; a version-form condition is the manifest's `stale_when_fired`, and `stale_when_unknown` is not fired) if present: when either has **fired**, the skip is revoked and the entry gets its full type-specific verification this run. **A fired expiry is NOT staleness** — it never by itself puts an entry in `stale_entries`; only the type-specific check failing does that (the one case where the expiry is that check is a `user memory` `pattern` entry, Task 4 above). List in `verified` the heading of every entry you ran a forced verification on — forced by a manifest flag or a fired expiry — whether it passed or failed. When the forced check **passes**, the expiry has done its whole job: the sweep re-dates `Verified` and clears the fired field (`shared/skills/qdream/memory-rules.md § Cross-type optional metadata`); for a `human:` entry it routes the passing check to the user instead of re-dating, never to you. You emit the heading in `verified` as an object whose `expiry` names the field that fired (`"Stale-after"` or `"Stale-when"`): the four governance-relationship classes are unchanged and `unrelated` is a strings-only list with nowhere to put a flag. A suspect forced only by a manifest flag is listed as a bare heading or `{heading, method}`, never with `expiry`. A `verified` item is the heading, or an object `{"heading": "<heading>", "method": "<method>", "expiry": "<field>"}` carrying only the keys that apply: `method` when you used a `Verified` method (`shared/skills/qdream/memory-rules.md § Memory File Format`), `expiry` only when a fired expiry forced this check. Return `anchor-reopen` only when you actually re-opened the `Source` anchor. An entry missing from `verified` is not re-dated. `expiry_fired` is carried **only** on a `stale_entries` item, where it tells § SYN-STALE that the item's real failing check was found during an expiry-forced re-verification. Emit the `Verified` actor alongside the date in `entry_verified` so the § SYN-STALE gate can see who last verified it.
> 5. **Pattern drift check** `[GAT-DRIFT]`: For each pattern-type memory entry, grep/glob to verify the pattern is still used in the codebase. For a `user memory` dispatch this task is a no-op: there is no codebase (Task 4).
> 6. **Identify improvement signals** `[GAT-SIGNALS]`: From session analysis, identify observations that suggest governance changes (skill edits, new rules, missing steering). Assess frequency (how many sessions) and impact (how much friction it caused). Each signal you emit here MUST carry a verbatim `evidence_quote` — the exact span grounding the observation, quoted word-for-word (the quote is load-bearing; prose secondary).
>
>    **In-session Skips.** A session with no project file may show the agent proposing an `[improvement_signal]` row in-session and the user explicitly choosing `Skip` (`shared/skills/qdream/memory-rules.md § Plan-less governance capture`). Return each such signal in `user_skipped`, with the proposal's heading and the user's Skip turn quoted verbatim. Only a Skip of a **new-row** proposal counts: a Skip of a proposed update to an existing row (adding this session to its `Sessions`) records nothing and is not returned. **Never return it in `improvement_signals` as well**, even when the same friction appears elsewhere in that transcript or in another session: the user's Skip decides it. A `user_skipped` item records a user decision, not a claim, so it does not go to the Cross-validation verifier. A signal the user chose `Save` for in-session is reported as usual, and also listed in `saved_in_session` with its row heading verbatim and this session's id, so the sweep can match an id-less `in-session` marker to this session and not count it twice.
>
> 7. **Harvest Claude Code's native project memory** `[GAT-NATIVE]`: Claude Code keeps its **own** per-project memory — an index file plus one file per entry — under `~/.claude/projects/<slug>/memory/`. It is never committed and no playbook read path loads it, so a durable entry written there reaches a committed memory file **only** through this task. Read `providers/claude/steering/memory-sources.md § Native project memory` for the layout, the **slug→workspace resolution** (via `~/.claude/history.jsonl`'s verbatim `project` field — **never** by inverting the lossy folder encoding), and the **native→playbook mapping table**. Translate with that table; do not invent a second mapping. **A slug directory that does not resolve to `{project_path}` is skipped quietly** — not an error, not a warning. Non-matches (a different user profile, a UNC path) are a normal outcome, and this task is a silent no-op for every project with no native memory directory.
>
>    Emit each translated entry as an ordinary `memory_proposals` item — **no new field, no schema change**: `type` from the native `metadata.type`, `source` carrying the native file path plus the legacy native ID from its `name:` frontmatter, and `evidence_quote` the native entry's own body span (the file *is* its ground truth). Apply `shared/skills/qdream/memory-rules.md § Native-memory harvest dedup` before emitting anything: gate 0 (already harvested — an existing `Source` names this native file or its legacy ID) emits nothing; gate 1 (translation-equivalence — the same fact in two formats, neither carrying anything the other lacks) proposes an update naming the existing heading; **anything less certain keeps both entries and is surfaced to the user at § DEC-GATE** — never merged by you.
