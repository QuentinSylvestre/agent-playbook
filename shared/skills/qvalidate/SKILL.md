# Validate

## Your role

Run the plan-file grammar's deterministic checks against one project file and report each as a machine-parseable result. This skill owns the check semantics; the lifecycle skills call `scripts/qvalidate.py` as a library at their existing checkpoints, and users may invoke it directly as a slash command. The script is the single implementation — this file is the single source of truth for what each check means and how callers react to a failure.

> **Citation convention**: Citations name sections, never numbers, and checks by their stable **name** (the TSV `<name>` field): `shared/AGENTS.md § SKILL.md Authoring`.

## The checks

These names are the cross-file citation vocabulary. Every other file (success criteria, call sites, the kiro overlay) cites these names; this section is where their meaning is defined. Names, not numbers.

- **`filename-grammar`** — the plan's basename matches `^[0-9]{6}_[A-Z0-9_]+\.md$` (`YYMMDD_UPPER_SNAKE.md`). Always PASS when a check line is emitted, because the applicability guard (below) already rejected non-matching basenames with exit 2; it appears in the suite so a passing run enumerates it explicitly.
- **`status-grammar`** — the `> **Status**:` line matches `<State>` or `<State> — <detail>`, where `<State>` ∈ `Exploring | Draft | In Progress | Complete` and `<detail>` is freeform. The match is anchored (a legacy hybrid such as `Complete (implementation + review) — …` is nonconforming, not prefix-passing) and tolerates the optional trailing template lifecycle comment every current plan carries. A missing status line is nonconforming. Emits **FAIL** (see the WARN→FAIL rollout note below for the one-time WARN phase used during introduction).
- **`completeness`** — when `<State>` is `Complete`, every `- [ ]` in the file must be ticked, **including** `(deferred from Phase N)` entries. This mirrors `/qdev` Step 9's deferred roll-up: an unsatisfied deferral is a blocker, not an exemption. FAIL when any box is unticked; PASS (not applicable) for any other State.
- **`phase-count`** — with `--phase N --expect-ticked K`: the number of ticked (`- [x]`) boxes inside Phase N's block (from its `### Phase N:` heading to the next `### Phase` heading) must equal K. FAIL on mismatch or a missing Phase N heading. When `K` is the literal `auto`, the check reports the ticked count as a PASS without comparing — no mismatch is possible. Fires only when the flags are supplied.
- **`parallel-symmetry`** — every phase in a `[P:N]` parallel group must annotate all its partners reciprocally: if Phase A declares `[P:B]`, Phase B must declare `[P:A]`, and every named partner phase must exist. FAIL on any asymmetry or dangling partner; PASS when no `[P:N]` annotations are present.
- **`sc-coverage`** — fires only when the Intent's Success criteria carry `SC-n` IDs. Every defined `SC-n` must be referenced by at least one phase `**Covers**:` line (FAIL on an orphan SC). IDs present but zero `**Covers**:` lines anywhere is a **WARN** (adoption nudge, not a failure). When no SC-n IDs are present, no check line is emitted.
- **`doc-updates`** — every row of the plan's `## Documentation Updates` table must name a target file that appears in `git diff --name-only <base>..HEAD` over the plan's commits. Severity follows the parsed State: **FAIL** when State is `Complete`, **WARN** otherwise — mid-plan an unimplemented phase's doc rows are legitimately absent. Rows marked `doc-table-only` in the `Phase` cell are skipped (the doc is updated outside any phase's file scope — e.g. an external wiki — which a diff cannot see). Rows naming a non-file target are also skipped; a section with no parseable file target is WARN. Every backticked path of the row's first cell is a target (else its first bare path). A target matches a changed file equal to it or ending in it at a path-segment boundary (`qclose/SKILL.md` matches `shared/skills/qclose/SKILL.md`, never `shared/skills/qdev/SKILL.md`), after stripping a trailing line anchor/list (`README.md:3`, `api.md:102,148`) and any trailing annotation after the first whitespace (`shared/AGENTS.md § Memory locations`); a brace set (`kiro_default.{json,md}`) matches when **any** expansion appears in the diff. Base-ref derivation follows `commit-pairing`. Fires only with `--check-commits`. WARN and skip outside a git repository. **Shared-branch caveat**: when a plan shares a predecessor's long-lived branch, `<base>..HEAD` includes the predecessor's own commits too, so a file the predecessor already touched passes **vacuously** before this plan changes it. Pass `--doc-updates-since <ref>` (the commit immediately before this plan's own first commit) to scope the scan to this plan's own contribution.

- **`harness-section`** — the plan contains a `## Harness Improvement Opportunities` heading. **WARN, never FAIL**, so Light/inline plans and legacy archives are unaffected. Mandated by `shared/AGENTS.md § Harness Improvement Capture`; consumed by `/qclose` Step 2 Pass 2 and `/qdream § GAT-PLANS`. An absent section is not a defect; an **unreported** absent section is — that is what this check surfaces.

- **`acceptance-evidence`** — every `User: accepted` in a markdown table row must carry evidence of the user turn it records. A row is a line whose first non-blank character is `|`. Fenced lines (```` ``` ```` or `~~~` at column 0) are skipped. Cells split on `|`, ignoring `\|`; then backtick code spans are removed from each cell, so a label quoted in code is not a hit and evidence in code does not count. Each `User: accepted` is a hit; its segment runs to the next hit in the cell or to the cell's end. A hit has evidence when its segment holds a marker, or when another cell of the row begins with a quote in a column whose header (the table's first row) names a user decision, answer, reply, turn or quote (a decisions table's `User decision` column). The markers are a non-empty quote (`"…"` or `“…”`; not `""` or single quotes), a `YYYY-MM-DD` date, or a reference, case-insensitive: `user turn`, `user answer`, `user decision`, `same turn`, `same user turn`, `decision <id>` (`decision 5a`, `decision D-14`, not `decision to defer`). A reference right after `pending`, `awaiting`, `no` or `without` is a negation and does not count (`pending user decision`); a quote or date in the same segment still does. `Follow-up <n>` alone is not evidence. A ticked `User acceptance:` list item outside a fence (any bullet or number, label case-insensitive) is a hit too, its segment the rest of the line. Other prose is never read. FAIL names each line with a bare hit; PASS counts the hits; no line when the plan has no hit. Severity is always FAIL, in every State. An error inside the check exits 2 (could-not-run). Known limits: two lone inch marks (`6" … 7"`) pair as a quote; evidence before the token in its cell does not count; a negation is caught only right before the reference (`pending a user decision` and `user decision pending` pass) and not inside a code span; an unescaped `|` inside a code span splits the cell, as in GFM; an indented fence does not toggle, a 4-backtick fence around a 3-backtick line flips the state, and rows inside HTML comments are read; a no-break space inside the label (`User:` NBSP `accepted`) is not normalised, so that text is not a hit; a bold label (`- [x] **User acceptance:**`) is not a hit either. Writing a new cell, record the turn as you write it (`/qdev`'s `Resolution column values` block); never add a marker to an existing row the user did not give.

- **`commit-pairing`** — with `--check-commits`: a **code commit** with no paired `docs(<slug>): …phase N` commit is FAIL. A code commit matches `<type>(<slug>): …phase N` where `<type>` ∈ `feat | fix | refactor | test | chore | ci` (the common-types list in `shared/AGENTS.md § Commit Conventions` minus `docs`, the paired commit's own type — `/qdev` Step 4 permits any of these for a phase, so matching only `feat` would miss real pairs). `<slug>` is derived from the plan filename. The base branch is derived via `git symbolic-ref refs/remotes/origin/HEAD` → local `main` → `master` → `--base <ref>`; when HEAD **is** the derived base, HEAD is on the base branch itself (a plan committed straight onto `main`, where `origin/main..HEAD` holds only the unpushed commits) or detached, or no base can be derived, a plan-scoped bounded window (`git log -n 400 -F --grep=<slug>`) is scanned instead, so unrelated commits on a long-lived branch cannot push a plan's pair out of range. WARN and skip outside a git repository. Fires only with `--check-commits`. **Renaming the plan file splits its slug history**: pre-rename `docs(<slug>)` commits grep for the old slug only, so pre-rename phases read as unpaired after a rename even though nothing was lost. Renaming an active plan is therefore **pre-execution-only** — never after a phase has landed a paired commit.

  **Foreign commit conventions — the convention discriminator.** `shared/AGENTS.md § Commit Conventions` makes the `<type>(<slug>)` grammar a *default* that a project's own stated convention outranks for commits landing in that project's repo; under a foreign convention the subject tests above would otherwise mismatch across the board, producing a **vacuous PASS** (or, when only the plan-bookkeeping half is foreign, a **spurious FAIL**). The script reads the plan file's own commit history from the plan root before pairing anything, treating it as ground truth for which grammar this repository writes plan commits in. Zero commits touching the plan file is *no evidence* — behaviour is unchanged. One commit whose subject starts with `<type>(<slug>):` (`docs` or any of the six code types) **certifies** the grammar and the scan proceeds as before — the `/qplan`-created `docs(<plan-slug>): …` commit alone certifies, and so does a hand-committed `chore(<slug>): add plan`. Commits that certify nothing produce a **WARN** naming the count scanned, and the pairing scan is skipped — the could-not-run third state in `## Failure semantics`. The `/qdev` Step 1/4 atomicity carve-out is unaffected. **Residual limitation**: foreign *code* commits paired with playbook-grammar *plan* commits still reach a vacuous PASS — the plan file certifies the plan-bookkeeping half only; the code half has no equivalent sensor.

**Full-suite rule**: every invocation runs the full applicable suite of the above — applicability is determined by inputs (flags supplied, State value, presence of SC-n IDs, git context), not by caller selection. The per-site check names listed under Call sites are each site's *motivating subset* — the reason that site invokes the validator — not a selection mechanism. There is deliberately **no** check-selection flag.

## Script contract

**Run the script. Never re-implement its checks inline.** The whole point of a deterministic validator is that its semantics are not re-derived per session — a hand-rolled equivalent reintroduces bugs the script does not have and makes its verdicts untrustworthy.

Copy-paste invocation (repo-relative):

```
<python> shared/skills/qvalidate/scripts/qvalidate.py [--project-root <dir>] [--plan-root <dir>] [--phase N --expect-ticked K|auto] [--check-commits] [--base <ref>] [--doc-updates-since <ref>] [--help] <plan-path>
```

`<python>` is the playbook venv's interpreter with `-I`: `<config-repo>/.venv-agent-playbook/Scripts/python.exe -I` (`shared/AGENTS.md § Config Repo Locations`), never a `python` from PATH. Run elsewhere, the script exits 2 with `guard did not run: venv missing`. `--selftest` runs its fixture suite. If flag syntax is unclear, read the script's own header rather than guessing at it.

**Flags**:

- `--project-root <dir>` — the **code root**: run git operations relative to `<dir>`, making the script cwd-independent. It no longer resolves `<plan-path>`; that half moved to `--plan-root`. Callers should pass this (or an absolute plan path) so the git scan is anchored. **The same flag name means something different in `close-plan.py`**, where it is "where `plans/` lives". That divergence is pre-existing and deliberate — the two scripts answer different questions — so it is documented apart, not unified.
- `--plan-root <dir>` — the **plan root**: resolve a relative `<plan-path>` against `<dir>`, and read the plan's own `docs(<slug>)` commits from that repository. Defaults to the directory holding the resolved plan, so the default is derived **after** `<plan-path>` resolution, never before it (the reverse order is circular). When `--project-root` is absent the code root **is** the plan root — the standalone `/qvalidate <plan-path>` case.

**Cross-repo (workspace store)**: when the plan lives in a store in the store repo (`shared/skills/qdream/memory-rules.md § Workspace Store`), pass `--project-root <code-repo-root>` **and** an absolute plan path (or `--plan-root <store>/plans`).

> **Name collision — read before passing the flag.** Two different things are called "the workspace" here. `--project-root` wants the **code repository** — where the implementation commits landed. The **store** is the workspace's directory in the *store* repo (`~/.agent-playbook/stores/<dir>/`, the path `store-resolver.py find` prints), and its `plans/` is what `--plan-root` wants. Passing the store to `--project-root` is a silent failure in validation: unlike archival, which refuses a cross-repository destination with exit 5, `qvalidate` has **no guard at all** here — it scans whichever repository you named and reports a confident `commit-pairing` answer about the wrong history. If a `commit-pairing` result surprises you, check which repository each flag pointed at first.
 `commit-pairing` then reads code commits from the code root and `docs(<slug>)` commits from the plan root, and its detail string reports both ranges as `code=<range> plan=<range>`. A plan moved into a store keeps its earlier `docs(<slug>)` commits where it used to live, so the check also reads them, by the plan-scoped window, from the code root and from the config repo (the repository holding the script, recognised by its `shared/` markers; the `QVALIDATE_CONFIG_REPO` environment variable overrides it, and an empty value skips it). The detail string then ends `earlier=code-root[,config-repo]`; `config-repo` is left out when that repository is the code or plan root's own, lacks the markers, or the override is empty. Give the override in the host's native path form (`C:\...` on Windows). The earlier homes are always read by the window, so in split mode a `docs(<slug>)` commit already on the base branch still pairs a branch code commit. If either root is not a git repository the check emits a `WARN` naming which one. Two documented limitations: `--base` serves the **code root only**, and `doc-updates` stays on the **code root**, so a Documentation Updates row naming a store-side file will not be seen.

**git floor**: the same-repo test is `git rev-parse --path-format=absolute --git-common-dir` equality, which requires **git >= 2.31**. On older git the flag does **not** error — `git rev-parse` echoes an unrecognised `--flag` to stdout and exits 0, so the result is non-empty garbage and two different repositories would compare equal. The script therefore gates on the **shape** of the result (an absolute POSIX or Windows drive-letter path), not on emptiness; anything else falls back to `--show-toplevel` and prints one `WARN` line on **stderr** (stdout keeps the CHECK/SUMMARY schema, and the warn counter is untouched). The fallback's known limitation: it cannot tell two linked worktrees of one repository apart, so a plan validated across two worktrees of the same repo would be treated as split.
- `--phase N --expect-ticked K` — enable `phase-count` for Phase N with expected ticked count K. The two flags are a matched pair. Pass the literal `auto` in place of `K` to skip the mismatch comparison and just report the ticked count — for the caller that does not yet know the expected count and would otherwise have to read it back out of a FAIL detail string on a first, throwaway invocation.
- `--check-commits` — enable the git-history scans: `commit-pairing` and `doc-updates`.
- `--base <ref>` — fallback base ref for `commit-pairing`, used only when neither `origin/HEAD` nor a local `main`/`master` resolves.
- `--doc-updates-since <ref>` — optional; scopes `doc-updates`' change-detection to `<ref>..HEAD` on the code root instead of the full `<base>..HEAD` range. Use when the plan shares a long-lived branch with a predecessor's own commits (see `doc-updates`'s shared-branch caveat above) — pass the commit immediately before this plan's own first commit. Absent, `doc-updates` behavior is unchanged.
- `--help`, `-h` — print the script header and exit 0.

**Output** (stdout, tab-separated):

```
CHECK<TAB><name><TAB><PASS|WARN|FAIL><TAB><detail>   (one line per fired check)
SUMMARY<TAB>pass=N warn=N fail=N                     (final line)
```

**Exit codes**:

- `0` — no FAIL among the fired checks (WARNs do not change the exit code).
- `1` — one or more checks FAILed.
- `2` — precondition failure: bad or missing path, a non-plan basename, a `plans/done/` file, or a malformed flag combination; or the guard did not run (`guard did not run: <reason>` on stderr, no SUMMARY): the venv is missing, git is not found or a git command it needs failed while `--check-commits` was given, a `--doc-updates-since` ref does not exist, or an unexpected error. That second kind is could-not-run (`## Failure semantics`). A shallow clone is not exit 2: `commit-pairing` WARNs that the history is shallow and the other checks still run.

**Applicability guard**: the script rejects, with exit 2, any file whose basename does not match `^[0-9]{6}_[A-Z0-9_]+\.md$` or that lives under `plans/done/` — these are not validatable active plans. Inline/Trivial plans have no file at all and are never passed to the validator (they inherit `/qdev`'s existing single-commit carve-out). **Known failure mode**: a basename carrying the *archived* convention's time suffix (`YYMMDD-HHMM_NAME.md`, `/qclose` Step 4's format) but living outside `plans/done/` rejects here too — the exit 2 is silent (no CHECK line at all), which reads as "nothing to report" rather than "the wrong convention was used." `/qexplore`'s own Step 3 filename spec already produces the correct no-suffix form for active plans; if a plan file exists but a qvalidate invocation against it produces zero CHECK lines, check the basename for a stray time suffix before assuming validation trivially passed.

## Failure semantics

**This section is the single owner of FAIL-handling behavior and guard-override discipline.** Call sites and the kiro overlay cite it by name; they never restate it.

On a FAIL (script exit 1): **halt**. Present the failing `CHECK` line(s) to the user **verbatim**. The user decides how to proceed. The orchestrator never interprets a FAIL, never works around it, and never re-runs the validator with modified arguments to make the failure disappear. A WARN is surfaced but is not a halt condition.

**Could-not-run is a third state — not a FAIL, not a PASS.** When a check cannot credibly run (missing dependency, unreadable input, a sensor reading that is obviously broken), surface it loudly as "validation could not run" and let the user decide. Never coerce it to FAIL (a broken checker would permanently block legitimate work) and never let it pass silently (that hides real failures). Distinct from the applicability guard's exit 2 on non-plan inputs, which is a routine by-design rejection needing no escalation. This three-state contract applies to every playbook guard script, not only this validator.

**Carve-out — `commit-pairing` at `/qdev` Step 1/4 (atomicity reconciliation).** When `commit-pairing` runs at `/qdev` Step 1/4 to detect an interrupted-session state, a FAIL (a code commit for phase N with no paired `docs` commit) is an *expected, recoverable* signal, not a halt: a prior session committed a phase's code but was interrupted before the orchestrator wrote the paired plan commit. The sanctioned response is the documented `/qdev` Step 4/7 reconciliation — adopt the dangling commit as that phase's implementation, apply the skipped plan updates, and emit the paired `docs` commit — which *completes* the interrupted work rather than working around a failure. The halt-and-user-decide default above governs every other site (`phase-count` at Step 7, `status-grammar`/`completeness` at `/qclose` Step 1, the `/qplan` commit points, the Step 8 stop gate). If the reconciliation cannot proceed cleanly (the dangling commit's phase is ambiguous, or its results-based exit criteria are unmet), fall back to the halt-and-user-decide default.

**Guard-override discipline** (renaming this paragraph label breaks citations — `/qreview`'s Verdict rubrics cite it by name)**.** Any sanctioned override of a guard verdict (severity-knob change, budget raise, carve-out use) must carry a stated reason recorded where the override lands (commit body, plan line, review log). A guard override without a justification is itself a review finding (Medium floor) per `/qreview`'s Verdict rubrics. Justified overrides form a distinct greppable audit category (existing instance: `verify-mass`'s commit-body override path). Machine parsing deferred until a script gains an override input (per `shared/AGENTS.md § Structure Requires a Consumer`).


## Call sites

The lifecycle skills invoke the validator at these named sites (Phase 3 of the introducing plan wires them — this section documents the contract; it does not itself edit those skills). Each site lists the check names that *motivate* the call; per the full-suite rule, the full applicable suite runs regardless. Every site handles a FAIL per `## Failure semantics` above (cited, not restated).

| Call site | Motivating checks |
|---|---|
| `/qclose` Step 2 Pass 1 (documentation gaps) | `doc-updates` |
| `/qdev` Step 1 & 4 (parallel-group / atomicity guards) | `parallel-symmetry`, `commit-pairing` (the Step 1/4 atomicity carve-out in `## Failure semantics` applies) |
| `/qdev` Step 7 (post-phase checkbox reconciliation) | `phase-count` (with the sub-agent's `exit_criteria_ticked` as K) |

## Library mode contract

When called as a library by a lifecycle skill, the caller:

- Ensures this file's rules are in active context before acting on a result.
- Invokes `scripts/qvalidate.py` with the venv `<python>` and an **absolute plan path, or `--plan-root <dir>` when the plan path is relative** (`--project-root` is the code root and does not resolve the plan path), plus any site-specific flags (`--phase/--expect-ticked` at `/qdev` Step 7 and `/qreview`; `--check-commits` at `/qdev` Step 1). A **relative** plan path is resolved against `--plan-root` when given and against `$PWD` otherwise — never against `--project-root`, which is the code root.
- Reads the TSV lines and the exit code, and applies `## Failure semantics` on exit 1.

**Non-playbook projects**: when the working project is not the config repo, resolve the script via the config repo location (`<config-repo>/shared/skills/qvalidate/scripts/qvalidate.py`, run with the venv `<python>` — path per `shared/AGENTS.md § Config Repo Locations`), mirroring `/qclose`'s archive-script convention. The invocation output (or a stated resolution failure) must be shown — substituting manual model reasoning for the script checks is a silent fallback and is not permitted; if the script cannot be resolved, say so and let the user decide.

The validator owns only the checks and their verdicts. It does **not** own auto-fix loops, review-log writing, or any caller-side gating — those stay with the calling skill.

## User-invokable mode

`/qvalidate <plan-path>` runs the validator directly against a project file and prints the TSV result. It emits **findings only** — it never edits the plan or the repository. The user reads the `CHECK`/`SUMMARY` lines and decides what to do. To include the commit-pairing scan, add `--check-commits`; to check a specific phase's tick count, add `--phase N --expect-ticked K`. A non-project file or a `plans/done/` file exits 2 with a clear message rather than validating.

## WARN→FAIL rollout

`status-grammar` now emits **FAIL**. During introduction it shipped as **WARN** so the new validator never hard-halted legitimate work on not-yet-normalized legacy plans; after the active plans in `plans/` were normalized, Phase 2 of the introducing plan flipped the default to **FAIL**. The severity is a single knob in each script (`STATUS_GRAMMAR_SEVERITY` / `$StatusGrammarSeverity`); there is no per-call-site strictness flag.
