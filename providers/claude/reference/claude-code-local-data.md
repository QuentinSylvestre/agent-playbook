## Claude Code Local Data

> **Reference only — not deployed.** Claude Code's session store, hook behaviour and status
> state machine, kept for cross-harness forensics. It loads on demand only — not in
> `inventory.tsv`, so it never reaches a Kiro session's context. **Read when** a `/qdream` sweep
> or a recovery task must read Claude Code's own session store, hook payloads or status state
> machine. Indexed from `memory/topics/kiro-cli.md`.

### Session files (primary conversation source)

Location: `~/.claude/projects/<encoded-path>/<session-id>.jsonl`

Each project workspace gets a folder under `~/.claude/projects/`. Folder names are derived from the workspace path by replacing non-alphanumeric characters with `-` (e.g., `C:\Users\alice\Documents\src\agent-playbook` → `C--Users-alice-Documents-src-agent-playbook`). A workspace below another one gets its own folder whose name extends the parent's, so a prefix match must stop at a `-` boundary (`...-Perso` must not match `...-Personal`).

Each session is a single `.jsonl` file named by its UUID (e.g., `50aa819f-667a-4d5b-af06-702f363e65d1.jsonl`).
Beside it, `<session-id>/subagents/agent-<id>.jsonl` (plus `agent-<id>.meta.json`) holds each sub-agent's
transcript, every record `isSidechain: true` with an `agentId` — measured on Claude Code 2.1.281,
2026-09-24 (one session, 9 sub-agent files). Older builds kept sub-agent turns inline, also flagged
`isSidechain: true`.

**Lines are large, so size a tail read in tens of KB.** Measured 2026-07-24 on Claude Code 2.1.219
across 1.9 GB of transcripts: median line 1,617 B, p95 19,136 B, max 154,917 B, and 24.7% of lines
over 4 KB. Final lines are disproportionately the large ones. A reader that seeks back N bytes and
drops the first partial line gets **nothing** when N is smaller than the last line: a 4 KB tail
recovered no complete line on 77% of 150 sampled transcripts, 16 KB failed on 12%, and 64 KB on 0%.

**Retention**: transcripts older than `cleanupPeriodDays` (default 30, `~/.claude/settings.json`) are
deleted (code.claude.com/docs/en/claude-directory.md, read 2026-09-24).

The `/qdream` sweep reads this store through `shared/skills/qdream/scripts/dream-manifest.py`; the
filtering rules it implements are in `providers/claude/steering/memory-sources.md § Session content filtering`.
Fork and background-handoff transcripts repeat earlier records under the same `uuid`s; the rule the
manifest applies to them is `providers/claude/steering/memory-sources.md § Forks and background handoffs`.

### JSONL message types

Lines are JSON objects with a `type` field. Known types:

| Type | Purpose | Signal value |
|---|---|---|
| `ai-title` | Session title generated by the model | Title extraction (primary) |
| `user` | User messages | Corrections, decisions, prompts |
| `assistant` | Model responses | Patterns, approaches |
| `mode` | Session mode (`normal`, etc.) | Metadata — skip |
| `bridge-session` | Bridge session linkage | Metadata — skip |
| `last-prompt` | Leaf UUID pointer | Metadata — skip |
| `file-history-snapshot` | File state tracking | Metadata — skip |
| `permission-mode` | Permission configuration | Metadata — skip |
| `hook_success` | Hook execution results | Metadata — skip |
| `hook_additional_context` | Hook-injected context | Metadata — skip |
| `deferred_tools_delta` | Tool availability changes | Metadata — skip |
| `agent_listing_delta` | Agent configuration | Metadata — skip |
| `skill_listing` | Available skills | Metadata — skip |
| `task_reminder` | Task context reminders | Metadata — skip |
| `command_permissions` | Permission grants | Metadata — skip |
| `compact_file_reference` | Compact file refs | Metadata — skip |
| `edited_text_file` | File edit records | Metadata — skip |
| `mcp_instructions_delta` | MCP instruction updates | Metadata — skip |
| `queue-operation` | Queue state | Metadata — skip |
| `file` | File content snapshots | Metadata — skip |
| `attachment` | Harness attachments (2.1.281) | Metadata — skip |
| `system` | Hook and stop events (2.1.281) | Metadata — skip |
| `cost-state` | Running session cost and per-model usage (2.1.281) | Metadata — skip |
| `atis-latch` | Harness state (2.1.281) | Metadata — skip |

**Per-record timestamps** (2.1.281, probed 2026-09-24): conversation records carry an ISO-8601
`timestamp` (420 of 603 records in the probed session; metadata types such as `ai-title`, `mode` and
`last-prompt` carry none). Transcripts from older builds may have none; date those records through
`history.jsonl`.

### Title extraction

Primary: `{"type": "ai-title", "aiTitle": "...", "sessionId": "..."}`
- First occurrence in the file is the canonical title.
- Fallback: first `type: "user"` message content (truncated to 80 chars).
- Last resort: session UUID.

### User messages

```json
{"parentUuid": "...", "isSidechain": false, "promptId": "...", "type": "user", "message": {"role": "user", "content": "..."}, "uuid": "..."}
```

The `parentUuid` field creates a tree structure (conversations can branch). For linear reading, process messages in file order — Claude Code appends chronologically despite the tree structure.

**Tool results are user-role records too.** A tool's output comes back as `type:"user"` whose
`message.content` is a list of `tool_result` blocks (with a `toolUseResult` field alongside) — 59 of 84
`type:"user"` records in the 2.1.281 probe. They are not user speech. 2.1.281 also stamps typed prompts
`origin: {"kind": "human"}`, and harness text `task-notification` or `peer`.

**`isMeta: true` means the record is NOT user speech.** Claude Code files harness-authored text under the `user` role: expanded `SKILL.md` bodies, the rendered stdout of a local slash command (a `/context` report arrives as a ~13 KB `type:"user"` record), and `<local-command-caveat>` blocks. Measured 2026-08-05: **213 of 1,737** text-bearing `type:"user"` records across 128 session files carry the flag. Any consumer treating user-role records as testimony — mining, memory extraction, `/qdream` — must skip them.

Necessary but not sufficient: compaction summaries (`"This session is being continued…"`) and task-notification blocks also arrive as `type:"user"` with `isMeta` absent, so judge those on content. Do **not** substitute a positional heuristic (skip-the-record-after-`local_command`): it matches 9 records, misses 208 of the 213, and false-positives on genuine user speech.

### Assistant messages

```json
{"parentUuid": "...", "type": "assistant", "message": {"role": "assistant", "content": [...]}, "uuid": "..."}
```

Content is an array of blocks (text, thinking, tool_use). Text content: `{"type": "text", "text": "..."}`.

**`message.usage` repeats per content block.** One API message is written as several `assistant`
records, one per content block, each carrying the same `message.id` and the same `usage` — 141 records
over 76 distinct ids in the 2.1.281 probe. Sum token usage once per `message.id`, and include the
`subagents/` files.

### Global history

Location: `~/.claude/history.jsonl`

Per-prompt entries recording user input across all sessions:
```json
{"display": "user prompt text", "pastedContents": {}, "timestamp": 1762383559299, "project": "C:\\Users\\...\\demo-app", "sessionId": "50aa819f-..."}
```

Fields:
- `display` — the user's prompt text
- `timestamp` — Unix milliseconds
- `project` — verbatim workspace path (with escaped backslashes on Windows)
- `sessionId` — present on most entries (absent on some early entries)

The `project` field is the reliable source for mapping folder names to real paths (folder name derivation is lossy — the history provides the reverse mapping).

### Active sessions — the liveness and live-status source

Location: `~/.claude/sessions/<pid>.json`, one file per running Claude Code process.

Not useful for session *content* — use the project `.jsonl` files for that. But this is the authoritative source for **which sessions are live right now, what they are, and whether they are working**, verified 2026-07-24:

```json
{"pid":51516,
 "sessionId":"3ee4f6fb-c84a-4681-8f91-e574a3c62300",
 "cwd":"C:\\Users\\alice\\OneDrive - ExampleCo\\Documents\\Dev\\src\\PowerAtlas",
 "startedAt":1784920809496,
 "version":"2.1.219","peerProtocol":1,
 "kind":"interactive","entrypoint":"cli",
 "name":"poweratlas-d2","nameSource":"derived",
 "status":"busy","updatedAt":1784933648496,"statusUpdatedAt":1784933648496,
 "bridgeSessionId":"session_01Rf9tLCfCkepzUgRuppBJEi"}
```

| Field | Use |
|---|---|
| `pid` → `sessionId` | The **process-to-session mapping**. A running `claude.exe` carries no session id on its command line, so this file is the only local way to attribute a live process to a session. |
| `status` | Live working state without tailing the transcript. Four values, read from the binary (`wDy=["busy","shell","idle","waiting"]`), not merely observed. |
| `waitingFor` | Present when `status` is `"waiting"`; a **free-form** human-readable reason, not a closed enum. |
| `statusUpdatedAt`, `updatedAt` | Epoch ms; gives freshness for the status above. |
| `startedAt` | Epoch ms. Compare against the process creation time to defend against **PID reuse** — the filename is a pid, and pids are recycled. |
| `cwd`, `name`, `kind`, `entrypoint` | Workspace attribution and a human-readable derived label. |

The status state machine, decompiled from the shipped binary:

```js
if (waitingReason !== undefined) return { status: "waiting", waitingFor: waitingReason };
return { status: isLoading || delegatedActive ? "busy" : "idle" };
// then, at the call site: idle + a shell command running -> "shell"

// waitingReason, in order:
//   sandboxHostPrompt || workerSandboxPrompt -> "sandbox request"
//   elicitationPrompt                        -> "input needed"
//   managedSettingsSecurityPrompt            -> "dialog open"
//   topDialogWaitingFor                      -> that dialog's own string
//   pendingWorkerRequest                     -> "worker request"
//   pendingSandboxRequest                    -> "sandbox request"
//   isShowingLocalJSXCommand                 -> "dialog open"
```

So `busy` and `shell` both mean working; `waiting` means a dialog is open and
blocking on the human; and **`idle` is ambiguous** — it covers finished,
errored and never-started alike, so it should not be read as "waiting for the
user". The write happens inside a UI effect keyed on the status value, so
`waiting` appears as soon as a dialog opens rather than at a turn boundary.

Other fields the reader accepts but that were not present in observed files:
`messagingSocketPath`/`sock`, `procStart`, `jobId`, `parkedJobId`, `logPath`,
`agent`, `state`, `detail`, `tempo`. `kind` is `vDy=["interactive","bg",
"daemon","daemon-worker"]`.

Caveats not established: whether the file is removed on abnormal termination,
and the transition latency of `status`. A headless `claude -p` run **does**
write one (observed appearing ~3 s after spawn and removed on exit).

The writer merges rather than replaces — it reads the existing file, spreads
the update over it, and rewrites in place. Consumers watching for changes must
therefore stat the file itself; the containing directory's mtime does not move
on a status change (observed: a file mtime 832 s newer than its directory's).

This is the Claude Code analogue of kiro-cli's `~/.kiro/sessions/cli/<id>.lock` (see `providers/kiro/reference/kiro-cli-v2-local-data.md § Session lock files`), and richer — the kiro lock carries only `pid` and `started_at`, with no status.

### Hooks

Configured in `settings.json` (`~/.claude/settings.json` for user scope, `<project>/.claude/settings.json` for project scope). The project file is **not** picked up by an already-running session — hooks instrument sessions started after the file exists.

Claude Code 2.1.219 carries zod schemas for **31 hook event types**. Extract the current list with:

```
python -c "import re; d=open(r'<path>\claude.exe','rb').read(); print(sorted(set(m.group(1).decode() for m in re.finditer(rb'hook_event_name:v\.literal\(\"([A-Za-z]+)\"\)', d))))"
```

Every hook payload carries `session_id`, `transcript_path`, `cwd`, and optionally `prompt_id`, `permission_mode`, `agent_id`, `agent_type`, `effort`.

Behaviour worth knowing before designing around them:

- **Hooks block the session, serially.** Each is awaited. A trivial forwarder costs ~280 ms per event (~4.5 s added to a 12 s session); a 5 s hook added 37.7 s. The `timeout` field caps damage but does not make them asynchronous. Do not spawn an interpreter per tool call.
- **No delivery guarantee.** Exactly one attempt per event, no retries. Failures — non-zero exit, unreachable endpoint, uncaught exception — are logged at DEBUG only and never surface to the model or the user. A dead endpoint degrades silently; a missed event is gone.
- **`SessionEnd` does not fire on abnormal termination.** A `taskkill /F` produced no terminal event, so anything tracking liveness from hooks alone will pin a killed session as active forever.
- **Unknown event names are accepted silently** by the settings schema, so a typo simply never fires.
- **Sub-agent tool events carry the *parent* `session_id`.** Only `SubagentStart`/`SubagentStop` carry `agent_id`, so events between them cannot be attributed by `session_id` alone.
- **`SubagentStop` fires before the parent's `PostToolUse` and well before `Stop`** — a rule that does not check `hook_event_name` will flip a session to "waiting" mid-work.

`PermissionRequest` and `Notification` **require an interactive terminal**. Four headless approaches produced neither, including two that recorded genuine `permission_denials`. Interactively:

- `PermissionRequest` fires ~1.2 s after `PreToolUse`, carrying `tool_name` and `tool_input`.
- `Notification` follows ~6 s later with `notification_type: "permission_prompt"`, message `"Claude needs your permission"`.
- A separate `notification_type: "idle_prompt"` (`"Claude is waiting for your input"`) fires **60 s after `Stop`**, once per idle period — not a heartbeat.
- `PermissionDenied` never fires, on either denial path, despite being in the schema.
- An **interactive rejection** yields `PreToolUse` → `PermissionRequest` → `Notification` → nothing further. A **`deny`-rule refusal** yields `PreToolUse` → `PostToolBatch` with the reason in `tool_calls[].tool_response`, and no `PermissionRequest`.

Permission rules match on tool name: on Windows the shell tool is often **`PowerShell`**, not `Bash`, so a rule written as `Bash(cmd:*)` silently never matches. A bare tool name (`"ask": ["PowerShell", "Bash"]`) matches every invocation of that tool.

### Session environment

Location: `~/.claude/session-env/<session-id>/`

Empty directories used as lifecycle markers. No useful content.

### CLI resume

```bash
claude --resume <session-id>
```

Must be run from the project directory (Claude Code scopes session lookup to the current project). The session-id is the `.jsonl` filename stem.

### Tool names and the permission surface

**The sub-agent tool is `Agent`, not `Task`.** Claude Code renamed it and current builds expose only `Agent`, so a permission rule written against `Task` is a **silent no-op** — it matches nothing and blocks nothing. Deny both names when a rule targets sub-agent dispatch. The execution family that must be denied together, because denying `Bash` alone leaves five other routes to a shell: `Bash`, `Task`, `Agent`, `Monitor`, `BashOutput`, `KillShell`.

**`--permission-mode` is an axis orthogonal to the allow/deny rule list.** Both apply and they stack: the mode selects a tier, the rule list filters individual tools. Modes (verified 2026-08-06 via `claude --help`): `acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk`, `plan`. Two distinct bypass flags exist and are not interchangeable — `--dangerously-skip-permissions` (bypass now) and `--allow-dangerously-skip-permissions` (make bypass available without enabling it). `/qfewer-permission-prompts` and the `update-config` skill both operate on the rule list only and never mention the mode axis, which is worth remembering when a permission problem resists a rule-level fix.

**Re-verify when** a permission rule silently stops matching after a Claude Code update, or a mode name errors as an invalid choice: `claude --help | grep -A3 'permission-mode'`.

### Native agent store

`~/.claude/agents/` holds Claude Code's own agent definitions, selected with `--agent <name>`. Claude Code owns their entire configuration — MCP servers, hooks, tools, model. The agent types a session offers resolve through this store.

The playbook deploys two Claude Code agent definitions, each an `inventory.tsv` symlink row: `qdream-reader` (`providers/claude/agents/qdream-reader.md`), the read-only child type `/qdream` phase agents launch, the counterpart of Kiro's `qdream_child`; and `qdream-phase` (`providers/claude/agents/qdream-phase.md`), the type the `/qdream` orchestrator launches each phase agent as. `qdream-phase` declares a `PreToolUse` hook in its frontmatter (`~/.claude/qdream-phase-hook.sh`, which runs `providers/claude/qdream-phase-hook.py` under the venv). A frontmatter hook runs only while that agent runs, so it needs no `settings.json` entry. The guard allows in Bash only one venv-python call of a qdream script subcommand a phase runs (an allow-list), writes only inside the work folder's `handoff/` (no orchestrator file, no alternate data stream), and only `qdream-reader` children launched with a child brief's prompt line. It fails closed: Claude Code lets a call through on any hook exit code other than 2, so the launcher exits 0 only on the guard's allow line and the command (`bash "$HOME/.claude/qdream-phase-hook.sh" || exit 2`, run in Git Bash on Windows) adds `|| exit 2` for a launcher that cannot run. Not yet observed firing in a live phase agent: verify with one dispatch after setup deploys it. A sub-agent's `tools` entry `Agent(<type>)` does not restrict the child type (Claude Code ignores the list below the main thread), which is why the hook checks `subagent_type`. A new file in an existing `~/.claude/agents/` is picked up by a running session within seconds. Neither has a counterpart of `kiro_default`.

**Re-verify when** `--agent <name>` stops resolving a name you expect, or the deployment inventory grows a Claude Code agent row.

### Native project memory

`~/.claude/projects/<slug>/memory/` holds Claude Code's **own** per-project memory, in its own format —
an index `MEMORY.md` whose lines are markdown links, plus one `.md` file per entry carrying YAML
frontmatter (`name`, `description`, `metadata.type`), an unlabeled instruction body, and `**Why:**` /
`**How to apply:**` paragraphs. kiro-cli 2.29.1 has a native store of its own
(`~/.kiro/memories/memories.db`, behind a server-side experiment flag;
`providers/kiro/reference/kiro-cli-v3-internals.md § Native memory store (2.29.1)`); no sweep harvests it
yet, so the playbook's `memory/MEMORY.md` is still the only memory Kiro sessions share with other harnesses.

This directory is **never committed**, so an entry written there is lost to every other harness until
the `/qdream` sweep harvests it (`shared/skills/qdream/sweep-gather.md § GAT-NATIVE`). A kiro session sweeping
Claude Code data needs to know it exists — that is why it is mirrored here.

The **canonical** layout note, the slug→workspace resolution (via `~/.claude/history.jsonl`'s verbatim
`project` field, **never** by inverting the lossy folder encoding) and the native→playbook mapping table
live in `providers/claude/steering/memory-sources.md § Native project memory`. Read that, not a copy —
this section is a discovery pointer, not a second source of truth.

**Re-verify when** the frontmatter key set changes, or the index stops being a flat markdown-link list.

### Path-keyed state (moving a workspace)

Measured 2026-10-02 (Claude Code 2.1.281-2.1.288, Windows) while moving six workspaces with
`shared/skills/qmigrate-workspace/SKILL.md`. Everything Claude Code keys by the workspace path:

| Where | What holds the path | On a move |
|---|---|---|
| `~/.claude/projects/<slug>/` | the folder **name** (slug), plus `cwd` on transcript and sub-agent records | rename the folder, rewrite the files inside |
| `~/.claude/history.jsonl` | `project` on each prompt record | rewrite `project` only; `display` is the user's text |
| `~/.claude.json` | keys of the `projects` map (per-project trust, MCP, tool approvals) | rewrite |
| `~/.claude/settings.local.json` | permission rules naming the path | rewrite |
| `~/.claude/sessions/<pid>.json`, `daemon/roster.json`, `jobs/*/state.json` | `cwd` | rewrite (runtime state, rewritten again by a live process) |

`/resume` lists the sessions of the slug folder that matches the current directory, so after the
rename, old sessions resume from the new path (user-confirmed 2026-10-02). A session whose first `cwd`
is elsewhere but which `cd`'d into the workspace stays in its own slug folder; its transcript only
mentions the path and needs no change. Claude Code rewrites `~/.claude.json` constantly, so every
Claude Code process must be closed while it is edited.

### Differences from kiro-cli

| Aspect | Claude Code | kiro-cli |
|---|---|---|
| Session storage | Single `.jsonl` per session (content + metadata) | Separate `.json` (metadata) + `.jsonl` (content) |
| Folder structure | Per-workspace folders under `~/.claude/projects/` | One `sess_<uuid>/` directory per session under `~/.kiro/sessions/<workspace-hash>/` (v3; `cli/` holds the retired v2 layout) |
| Sub-agent sessions | `<session-id>/subagents/*.jsonl`, records `isSidechain: true` (2.1.281; inline in older builds) | `sub-executions/<uuid>.jsonl` inside the parent's session directory; no `parent_session_id` field |
| Title source | `ai-title` type entry in `.jsonl` | `title` field in `.json` metadata |
| Message format | `type` field discrimination (`user`, `assistant`) | `payload.type` discrimination (`user`, `assistant`, `tool_result`) in `messages.jsonl` |
| Timestamps | Per-record ISO `timestamp` (2.1.281); none in older builds — date via `history.jsonl` | Per-record `timestamp` in `messages.jsonl`; `createdAt`/`lastModifiedAt` in `session.json` |
| Resume command | `claude --resume <id>` (from project dir) | `kiro-cli chat --resume-id <id>` (from any dir) |
| Path encoding | Folder name = path with non-alphanumeric → `-` | Workspace-hash folder; the path itself is `workspacePaths` in `session.json` |
| History | Global `history.jsonl` with per-prompt entries | Per-session `.history` files |
| Project memory | Native store at `~/.claude/projects/<slug>/memory/` (index + one file per entry), never committed | No native store — the playbook's own `memory/MEMORY.md` |
