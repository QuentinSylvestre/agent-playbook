## Governance retirement (qdream)

These reinforce Governance retirement proposals added to `## Phase 4b — Decisions`; spelled out here because the kiro model must be able to propose *removing* rules, not only adding them, yet never strip a guardrail. Full mode only.

- **Propose removals, not only additions**, when a gate-verified signal or demoted entry shows a rule is stale, contradicted, or superseded, or a prior edit's `outcome_tags` came back `recurred`. Do NOT propose retirement on a "nothing relies on this" hunch — reliance is not measurable yet, so that rationale can only be confabulated. Present as a Dream Governance Proposal, `Apply / Skip`, one at a time.
- **Every retirement Rationale must cite its grounding evidence** — the verbatim `evidence_quote`, the demoted entry's contradicting provenance, or the `outcome_tags` record. No grounding, no proposal.
- **Never propose retiring a safety or correctness gate.** A behavioral contract, non-obvious procedure, data-integrity rule, or any guardrail whose removal would change behavior or weaken protection is not a retirement candidate — verbosity is a rewrite candidate, not a removal candidate.
- **The guard pins headings, not bullets; the pre-proposal check is the real gate.** Before proposing, check the target against `shared/skills/qconfig-sync/scripts/citation-checks.tsv` — a guarded heading is never a candidate. There are no commit-time hooks; the guard is a delayed backstop firing only at the next `/qconfig-sync`, so this pre-proposal check — not the guard alone — is what actually stops a bad retirement.

## Quiet-project counters (qdream)

These reinforce the `quiet_sweeps` update in `§ APP-STATE` and the user-memory `Keep` in `§ APP-ADJUDICATE`; spelled out here because the kiro model must not reset a counter on a pass that did not finish. Full mode only.

- **`state apply` computes a counter for every confirmed project with a memory file**, stamped or not, under its `state_key` when the manifest has one; you write none (`state-inputs.json` has no `quiet_sweeps` key), and the rules below are what it computes. `0` only when its file's `task4_status` is `checked` after the count-verify; otherwise the manifest's `quiet_sweeps` + 1 — a quiet, failed, skipped or truncated pass all count + 1.
- **A user `Defer` on a subsumption or stale item sets that project's counter to `4`**, whatever the pass returned, so the next sweep checks it again.
- **User memory resets to `0` only after a pass that dispatched every file with every file `checked`** — `periodic`, or `flagged` with the counter at 4 or more. A pass over only the trigger-flagged files counts + 1. A declined or excluded project keeps its value; a removed project's key is deleted.
- **`Keep` on an expiry-only user-memory stale item re-dates it.** The gate shows the re-dated entry: `Verified` as today with a `human:<id>` actor naming the user, and the fired `Stale-after`/`Stale-when` removed, so it does not come back every sweep. The Apply phase agent carries it out as one `memedit` `replace` op naming the item's `decision_id`, its text exactly the shown entry; never write the line yourself. Every other stale-item `Keep` changes nothing.

## Human-attested expiries (qdream)

These reinforce the human-attested expiry item in `## Phase 4b — Decisions` (§ DEC-GATE) and its executor in § APP-ADJUDICATE; spelled out here because the kiro model re-dates a passing check by habit and must not do so for a `human:` entry. Full mode only.

- **A passing expiry check on a `human:` entry is its own gate item at § DEC-GATE, never re-dated by you.** Show the heading, its memory file, the current `Verified` line, the fired field with its full text, and the method if one was returned. Three actions: `Keep` re-dates `Verified` as today with `human:<id>` naming the user, no method, and removes the fired field; `Re-date-as-sweep` re-dates with actor `sweep` plus the returned method, if one was returned, and removes the field; `Defer` changes nothing. There is no `Delete`. The gate shows the whole re-dated entry, and Apply writes exactly that text with one `memedit` `replace` op; never edit the entry yourself. Count `Keep` and `Re-date-as-sweep` in the Report's `Updated:` user-gated count, and report the item in `Human-attested expiries`. Name each merge that dropped a `human:` actor in `Attestations lapsed on merge`. A heading in `human_expiries` is not offered for promotion this sweep: a rule whose human-written expiry just fired is re-attested before it is promoted.

## Drafters, gate items and Apply (kiro)

These reinforce § DEC-PROPOSALS (Drafter dispatch, Gate item format), § Dream Drafter Brief, § APP-ADJUDICATE and § APP-COMMIT; spelled out here because the kiro model must hand the user text it can decide on cold, and Apply must write exactly that text and nothing else. Full sweep only.

- **Synthesize and Apply phase agents: read the kiro phase-agent rules first** — `<python> <skill-dir>/scripts/dream-check.py extract --file <skill-dir>/SKILL.md --section "## Phase agents and handoff files (kiro)"` — and follow them: never a question to the user, a `needs-decision` instead.
- **Drafter dispatch, in order** (the Synthesize phase agent). Per proposal run `dream-sweep.py blast --file <target> --heading <heading> --snapshot-sha <sha>`; a target outside the config repository gets no `blast` run, `blast: null` and an absolute `target_file`. Write `handoff/drafts.json` and run `handoff check drafts.json`. Run `dream-sweep.py brief --kind drafter --items drafts.json --snapshot-sha <sha>` and launch each drafter with its printed line, at most 5 per batch, on the `drafter` model `orient.json` names. Collect each draft with `extract --kind drafter --label <label> --kiro` (the inbox only as the fallback the kiro phase-agent rules allow). A draft `extract` refuses, or a drafter with no draft, is a child failure. Join a draft to its proposal only through its record's `data` and `data_sha256`, never by label order.
- **A drafter is read-only.** Read, Grep and Glob only: it runs no script, writes no file and dispatches no agent. When it cannot locate the target text it returns `current_text` and `after_heading` `null` with `notes` saying why; it never guesses.
- **Every gate item is readable cold.** `dream-sweep.py gate` writes `gate.md` and every drafted item in it; you write only `gate-items.json` (a drafted item's `why` and `options`, every other item's whole `text`) and never `gate.md`. The Gate item format of § DEC-PROPOSALS, every line in its order: `Gate item <id>:` with the observable behaviour change; `Why:` with the evidence count and one quoted example; `File:` with the repository name in full (never "this repo"); `Current text:`, or `New file: <repository name> <target file>` for a draft with `create: true`; `New text:`; `Already covered by:`; `Also edits N other sites:`; `Memory entries that cite it (not edited by this sweep):` (shown only, never edited); `Also cited by (not edited by this sweep):` (non-`.md` hits the user updates by hand after Apply); `Options:` with the recommendation first. End `gate.md` with `End of gate: <N> items` (`End of gate: 1 item` for one). Show the whole item inside the question, never "see above".
- **Approved text is the written text** (the orchestrator). Never write `decisions.json` yourself: write the user's answers to `answers.json` and run `dream-sweep.py decisions --snapshot-sha <sha> --gate-sha <sha>`, which copies each governance item's `target_file` and `heading` from `drafts.json`, and each Applied item's `current_text`, `after_heading`, `create`, `new_text` and `blast_edits` from its extracted draft (`sweep/drafts/<label>.json`), never from `gate.md` or a retyped copy, after checking each text appears verbatim in the item's `gate.md` text. A refusal is a child failure of the Synthesize phase: do not present the item.
- **The governance path rule — Apply edits only these.** An Applied governance target or blast edit is a `.md` file inside the config repository or, as an absolute path, under a manifest project root. Never a path with a `memory`, `.git` or `..` component, a `:` beyond a leading drive letter, a component ending in a dot or space, a link reaching memory or `.git`, or a memory file. A blast edit names a blast hit of its item or its `target_file`. A new file is written only for `create: true` on a target that did not exist at Orient. A CODE item is never Applied in the sweep. `handoff check decisions.json` and every `dream-write.py` call refuse any other path: a refusal is final, never worked around.
- **Apply exactly, byte for byte** (§ APP-ADJUDICATE). Edit a governance file only where it still holds the item's `current_text` exactly once. On a resume (`shared/skills/qdream/sweep-handoff.md § Resume`) a file that does not hold it is not at once a `needs-decision`: it resumes from the longest prefix of its items (the Orient content plus the first k replacements) that matches, and applies item k+1 onward; a file whose whole content passes the `hash --record` test counts as already edited, and one equal to its Orient content as unedited. Only a file matching no prefix is a `needs-decision` (do not edit it, write the file, and end). Write each edit as one replacement of the whole `current_text`, never split into smaller ones. When a write is refused, write a `needs-decision` of kind `failure` naming the item, quoting the refusal and listing every governance file already edited with the id of every item whose edit landed there, and end: never revert, never finish the item another way. Only after the last Applied edit of every item has landed, run `dream-write.py hash --record --decisions <work>/handoff/decisions.json --decisions-sha <sha> --snapshot-sha <sha> <file>` once per edited file. Every memory write is a `memedit` op in `handoff/ops/app-adjudicate.json` naming its item's `decision_id`, `file`, `heading` and the shown text. An op `memedit` refuses is never retried under another `decision_id`, class or text: write a `needs-decision` of kind `failure` naming it, and end.
- **Commit only through the script, without `--track`** (§ APP-COMMIT, the Apply phase agent). Run `dream-write.py commit --repos <every repository in orient.json's repos> --usage-line "<the Usage from plans line>" --decisions <work>/handoff/decisions.json --decisions-sha <sha> --snapshot-sha <sha>`. It takes no `--track`: it reads the untracked files to commit from `decisions.json`'s `track` list itself. Never run `git add`, `git commit` or `git push` yourself. Exit 3 with a `--repos … is not the top of a git repository` line committed nothing: fix the list and run it again; any other exit 3 means one repository was refused or failed while the others were committed, so record it and go on. Write `handoff/apply.json` with `push_plan` `null`: the push plan and the push are the orchestrator's.
