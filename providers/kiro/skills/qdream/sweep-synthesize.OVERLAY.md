## Cross-validation gate (qdream)

These reinforce the Cross-validation gate added before § SYN-WRITE in `sweep-synthesize.md` (this overlay merges into it); spelled out here because the kiro model must not shortcut the verifier or rubber-stamp its output. Full mode only.

- **You are the Synthesize phase agent: read the kiro phase-agent rules first.** Before your first step run `<python> <skill-dir>/scripts/dream-check.py extract --file <skill-dir>/SKILL.md --section "## Phase agents and handoff files (kiro)"` and follow it: verifiers and drafters through `subagent_qdream_child` (never `subagent_kiro_default`), returns through `extract --kiro` (the inbox only as that section's fallback), never `wait`, never a question to the user. Render verifier briefs with `dream-sweep.py brief --kind verifier` and launch each with the exact line it printed; after the last batch, `aggregate` must report nothing `missing`.

- **The verifier's job is to REFUTE, not approve.** One adversarial verifier sub-agent per project (or per harvest batch, below), dispatched before any autonomous write, actively looking for claims the quote doesn't support. Do not skip this because the quotes "look fine".
- **Read-only, stated up front** — `Read`/`Grep`/`Glob` only; read-only, run no scripts, and may not dispatch further sub-agents (`shared/AGENTS.md § Dream autonomy exception`) — so it does not probe for its limits.
- **PASS must quote the entailing span verbatim, or it defaults to refuted.** A bare "yes, entailed" with no quoted span is not a valid verdict.
- **Spot-check quotes with a floor, never an unfloored "sample".** Every item at ≤10 items per project, at least 10 above that, prioritizing items driving a write or promotion. A quote not actually in its source is refuted regardless of entailment.
- **One verifier dispatch per project or harvest batch — § SYN-PROMOTE reuses the verdict**, never a second verifier; a refuted signal is dropped, not re-checked.
- **Harvest batches follow the per-project rules per member project.** The `HARNESS_HARVEST:` signals you built for projects without an `all tasks` agent go ONLY to harvest batches of at most 25 items that hold nothing else, never to a per-project verifier. Inside a batch, count the spot-check floor over each member project's own items (all of them at 10 or fewer, at least 10 above that), never over the batch. An item left without a verdict defaults to refuted for its own project. A batch that fails to dispatch downgrades EVERY member project to user-gated `Save / Skip`.
- **On dispatch failure, degrade — never write unverified content.** A verifier that fails is a child failure: write a `needs-decision` of kind `failure` and end; never ask, wait or retry yourself. The orchestrator relaunches you once, then asks the user `Retry / Skip / Abort` on a second consecutive failure (`shared/skills/qdream/sweep-handoff.md § Failure gate`). On the user's Skip, downgrade that project's writes to user-gated `Save / Skip` for this run only. A verifier stopped by a session or token limit is not a dispatch failure: write a `needs-decision` of kind `rate-limit` (with `reset_at`) or `budget`, naming the unverified items, and end; never downgrade the run for it.
- **The verifier also tests subsumption and narrowing, with no residue.** A `subsumed_entries` quote must be verbatim, **normative** (never an Exclusion-List row or a quoted counter-example), and entail the entry including its `How to apply`, not only its claim — "do X" against "do X except Y" is NOT subsumed. A `not_a_conflict` narrowing that doesn't hold is re-routed to `governance_conflicts`.

## Utility pruning & rejected lessons (qdream)

These reinforce the derived-utility prune order (`shared/skills/qdream/memory-rules.md § Derived Utility & Pruning`; scopes in `shared/skills/qdream/memory-rules.md § Session-start memory context budget`) and the rejected-lessons suppression store added to § SYN-WRITE's Size check; spelled out here because the kiro model must prune by measured value, not age, and must not re-propose an already-rejected reflection. Full mode only.

- **Prune by derived utility, not by age.** Follow `§ Derived Utility & Pruning` exactly — do not paraphrase it from memory. Two points this model gets backwards: `Stale-after`/`Stale-when` are NOT prune inputs — only a verification *failure* lowers utility; and a `human:`-verified entry is never selected for pruning, whatever it ranks on (1)-(5).
- **Never propose a prune.** `apply-all` removes what is over each tier's budget by the owning order, and never a `human:` entry or a `memory/HIGHER_ORDER.md` node.
- **`Outcome` may be absent — treat it as neutral, never invent one.**
- **Bump `Usage` by 1 (at most once per entry per sweep)** when this sweep merged into or referenced the entry, before the Size check runs. **Plan headers**: bump from a new plan's `memory_relied_on` heading only when it matches exactly ONE entry across the project memory, `memory/MEMORY.md` and `memory/topics/*.md` (exact match after whitespace and case normalization). Headings are separated by ` | `; a `;` stays inside its heading. Zero or two-plus matches, or a heading the manifest cut (`memory_relied_on_truncated.shortened`): bump nothing, name the heading as unresolved in the Report's `Usage from plans` line, with the count of headings the 20-heading cap dropped. Never pick the likelier candidate. Never bump from a plan header by any other path.
- **Never prune an `[improvement_signal]` entry.** Leave it out of a project memory file's entry count, so it never pushes a verified entry out; count it only in `memory/topics/improvement-signals.md`. Only an `Apply` at § APP-ADJUDICATE removes it, plus one expiry: after the re-observation updates, a signal still at `Frequency 1` whose `Last observed` is more than 90 days old is removed at § SYN-PROMOTE as removal class `expired_signal`, journal-first, and named in the Report. A signal at `Frequency` 2 or more never expires; a missing `Last observed` never expires one. User-scope signals live in `memory/topics/improvement-signals.md`, never `memory/MEMORY.md`: § SYN-PROMOTE persists a new one there. For a re-observed one, before the gate and whichever path follows, append this sweep's new session ids to its `Sessions` field (no duplicates), then set its `Frequency` to the number of distinct ids in `Sessions`; never increment `Frequency` on its own. When the orchestrator or you, the Synthesize phase agent, observed the friction this run, list that session (the orchestrator's ids are the file names, without `.jsonl`, of the transcripts `orient.json`'s `orchestrator_sessions` lists) as `sweep <YYYY-MM-DD> <session-id>` (or `sweep <YYYY-MM-DD>` with no id), project last — never an empty token like `**Sessions**: , agent-playbook`.
- **Record rejected lessons; consult them next sweep.** A verifier `refuted` proposal, or a user Skip of a gate-verified governance-rule/improvement-signal proposal, appends to `.dream-state.json` `rejected_lessons`. The two reach it differently. A refuted one is written to `synthesize.json`'s `rejected_lessons` by the Synthesize phase agent and copied by the Apply phase into `state-inputs.json`. A user Skip happens at the gate, after Synthesize ends, so no Synthesize file can hold it: the Apply phase agent writes it into `state-inputs.json` from the Skipped item in `decisions.json`, with `item` set to that item's id (none for an item carrying `for_conflict` or `skip_item`). Only `dream-write.py state apply` at § APP-STATE persists either; never write the state file yourself. A **memory-proposal** Skip is different — it writes a `## Declined` row instead, never both for one Skip. A refuted `not_a_conflict` or `stale` Task-4 verdict never goes to `rejected_lessons`.
- **Record only explicit judgments** — an examination gap (no verdict, truncation, bulk triage) is never a rejection.
- **Suppression is bounded**: drop a `skipped` record after 60 days, a `refuted` after 180. Do not suppress a proposal re-surfacing with fresh grounded evidence — a quote dated after the record, in 2+ distinct new observations. Day-granularity tie rules: `shared/skills/qdream/memory-rules.md § Date References`.

## Outcome tagging (qdream)

These reinforce Outcome tagging (before § SYN-WRITE) and the applied-edit recording in § APP-STATE; spelled out here because the kiro model must not skip the follow-up measurement or fabricate an outcome. Full sweep only.

- **Grade past edits, don't just make new ones.** For each unresolved `outcome_tags` record, decide `recurred`/`not-recurred`: recurred iff a Cross-validation-gate-**confirmed** `improvement_signal` still reports the same friction against the same `target`, dated after `applied`. `insights_signals` alone (not gate-verified) can never stamp `recurred`. If the target's project wasn't analyzed this sweep, leave it unresolved — never guess.
- **Rule 7 holds** — compute off the sub-agents' structured signals and their evidence dates, never a transcript.
- **Record at apply time, resolve later.** Append `{target, applied: today}` when the user Applies an edit; a later sweep fills in `outcome`/`checked`.
- **Feed both consumers.** Stamp a memory entry's `Outcome:` field for the derived-utility prune; a governance-edit's `recurred` outcome feeds the retirement pass below.

## Dual store & higher-order tier (qdream)

These reinforce Episodic replay ledger + higher-order synthesis (the named step after § SYN-INSIGHTS in `sweep-synthesize.md`) and the `memory/HIGHER_ORDER.md` tier (`shared/skills/qdream/memory-rules.md § Higher-Order Tier`); spelled out here because the kiro model must actually build the dual store — episodes AND compounding abstractions — not just write flat memory entries. Full sweep only.

- **Two stores, both written every full sweep.** The episodic ledger (`.dream-state.json` `episodic_ledger`) is append-only. `memory/HIGHER_ORDER.md` is the semantic store, one rung above `memory/MEMORY.md`.
- **Plan ledger records before any node cites them.** Write the new records to `handoff/steps/SYN-HIGHERORDER.json` under `records` and run `dream-write.py state ledger --plan --inputs steps/SYN-HIGHERORDER.json --snapshot-sha <sha>`; cite only the indices it prints. On a first run (no state file) it refuses: leave the records in that file for the Apply phase. Write nodes only through queued ops, never with an edit tool.
- **Induce a node from its Support-set — never invent one.** A node's claim must be entailed by the episodes and entries its `Support-set` names, never general knowledge or your own opinion. This is the ONE autonomous write the Cross-validation verifier never sees, so the `Support-set` is the node's only grounding check.
- **Read the prior nodes first, so the tier compounds** — update them, do not re-derive from scratch.
- **At or over the user-memory word pin, update a node — never add one.** `memory/HIGHER_ORDER.md` counts toward `MEMORY_BUDGET_WORDS` (read the `memory` row of `dream-check.py budget`, never restate the number) but is never pruned. So when that row is at or over the pin, fold a new abstraction into the node it extends; if none fits, write nothing and name it in the Report's `Stages` line. Never delete a node here: removal stays `Keep node / Remove node / Defer`. Read the episodic ledger through its window (this sweep's appends plus the most recent 50 prior records), never the whole ledger.
- **Write `Support-set` pointers in the grammar, or the next sweep cannot resolve them — never point at a governance section.** The project qualifier on a `project memory (<project-path-key>)` pointer is MANDATORY: a bare heading, or a basename shared by two projects, is `indeterminate` — never guessed. Full grammar: `shared/skills/qdream/memory-rules.md § Support-set referential integrity`.
- **`Affirmed` is the only persisted state a node carries.** Preserve it verbatim on a content-only update; drop it only when you change the `Support-set`.
- **Two pointer populations, only one reconciled.** Node pointers are live references, resolved fresh every sweep. Ledger `support_set` pointers are history — NEVER reconcile, re-point, or rewrite them; a dangling ledger pointer is correct, not a defect.
- **Reconcile in order: re-point renamed targets, then resolve, then classify.** Resolving first drives a node with intact ground to the deletion gate. Classify `resolved` / `confirmed-absent` (the sweep looked, it's gone) / `indeterminate` (the sweep could not look — never treat as absent). A node is ungrounded only if it has ≥1 pointer and EVERY pointer is `confirmed-absent`; any single `indeterminate` blocks the gate.
- **A dedup merge (`§ Merge Strategy`) never removes an entry, only renames it** — handled by re-pointing, never a removal.
- **The tier loads at session start mechanically** — the agent definition's config-repo glob `"file://{{PLAYBOOK_ROOT}}/memory/*.md"` delivers it from any working directory; treat it as advisory context to verify, not commands.

These reinforce the dedup-merge lapse record in `§ SYN-WRITE` of `sweep-synthesize.md`; spelled out here because the kiro model must report a merge that drops a person's attestation, not only perform it. Full mode only.

- **Record every merge that drops a `human:` actor.** When a merge's surviving `Verified` no longer carries the `human:` actor the replaced entry's carried (it carries any actor other than that `human:` id, for example after a verifying merge, or after a non-verifying one whose newer surviving date carries `sweep`), record the surviving heading at § SYN-WRITE for the Report's `Attestations lapsed on merge` line. The merge rule itself does not change.
